Databases and data services

What decides PQ here

Two TLS stacks meet on every database connection. The server engine (its version, its group setting and the TLS library it links) decides which groups it accepts; the client driver's TLS stack decides which groups it offers. Hybrid X25519MLKEM768 needs both sides to support it, TLS 1.3, and no setting on either side that pins a classical list.

On managed services AWS owns the server stack, so you change a parameter group or the engine version. On self-managed engines you choose the image and set the engine's group option, or an OpenSSL config file where the engine has none. Tests in this tab ran on 2026-11-14 (arm64 Docker); scripts and output are kept in the data work directory.

Server side

RDS for PostgreSQL 18 and Aurora PostgreSQL 18

  • Parameter group family postgres18 (RDS instance) or aurora-postgresql18 (Aurora, cluster parameter group).

  • ssl_groups: hybrid first, classical after for fallback: X25519MLKEM768,SecP256r1MLKEM768,X25519,prime256v1. Use commas in the API, Terraform and CloudFormation (Claimed: the RDS API rejects colon lists).

  • rds.force_ssl = 1 (default on 15+).

  • To enforce PQ: ssl_groups = X25519MLKEM768,SecP256r1MLKEM768 and ssl_min_protocol_version = TLSv1.3, because ML-KEM needs TLS 1.3 (Documented).

aws rds modify-db-parameter-group --db-parameter-group-name pg18-pq \
  --parameters "ParameterName=ssl_groups,ParameterValue='X25519MLKEM768,SecP256r1MLKEM768,X25519,prime256v1',ApplyMethod=immediate"

Full Terraform and CloudFormation are in Full configuration files.

RDS and Aurora MySQL, RDS for MariaDB

  • Aurora MySQL: upgrade to 8.4.8+ (8.4-compatible line) or 3.14.0+ (8.0-compatible line); no parameter. Check SHOW STATUS LIKE 'Aurora_ssl_named_group'. Keep require_secure_transport = ON and tls_version = TLSv1.2,TLSv1.3; TLS 1.2 clients stay classical.

  • RDS for MySQL 8.4.11 and RDS for MariaDB (12.3.3, 11.4.13, 11.8.9): upgrade the minor version. The enabling parameter is not confirmed here. After the upgrade, list the parameter group for a groups or PQ parameter and probe with s_client (Verify).

Self-managed PostgreSQL 18 (Tested)

# postgresql.conf (excerpt)
ssl = on
ssl_groups = 'X25519MLKEM768:X25519:prime256v1'   # PG 18 name; ssl_ecdh_curve is an alias
ssl_min_protocol_version = 'TLSv1.2'               # 'TLSv1.3' to enforce PQ

hostssl lines in pg_hba.conf reject non-TLS clients. SELECT pg_reload_conf(); applies TLS settings to new connections.

Self-managed MySQL

  • 8.4 LTS and 9.x: no PQ on the server, even linked to OpenSSL 3.5.8 (Tested). Plan for MySQL 26.x.

  • 26.x: PQ on by default (Tested). Variables (Documented, MySQL 26.10 manual): tls_kex (colon list, case-sensitive names), force_pqc, use_pqc_sign, each with admin_, replication_, group_replication_ and mysqlx_ variants. Status: Tls_key_exchange_algorithm, Tls_sign_algorithm.

  • Version history: server-side PQC (PQ groups, force_pqc) was added in MySQL 26.7.0 (MySQL 26.7 manual, Documented); 26.10 adds the MySQL Shell and client options tls-kex and force-pqc. Any 26.7+ server qualifies; the tests here used 26.10.

# my.cnf (excerpt)
[mysqld]
require_secure_transport = ON
tls_version = TLSv1.2,TLSv1.3
tls_kex = X25519MLKEM768:secp256r1MLKEM768:X25519:secp256r1
# force_pqc = ON          # enforcement: classical clients fail (Tested)

Self-managed MariaDB, Valkey, Redis OSS

No group option of their own was found. They follow OpenSSL's defaults, which on OpenSSL 3.5 put X25519MLKEM768 first. To change the order or enforce PQ-only, point OPENSSL_CONF at a file with Groups = ... (Tested on Valkey 8.1.11: the PQ-only file rejected an X25519-only client).

# valkey.conf (excerpt)
port 0
tls-port 6379
tls-cert-file /etc/valkey/tls/server.crt
tls-key-file  /etc/valkey/tls/server.key
tls-ca-cert-file /etc/valkey/tls/ca.crt
tls-protocols "TLSv1.2 TLSv1.3"

Kafka and Cassandra (JVM)

The broker's JDK decides. Run JDK 25.0.5+ (PQ by default) or attach the Bouncy Castle JSSE agent from the Java tab. Kafka: ssl.enabled.protocols=TLSv1.3,TLSv1.2. To pin groups, set -Djdk.tls.namedGroups=X25519MLKEM768,x25519,secp256r1 in KAFKA_OPTS. Not tested on a broker (Unverified).

Verify

  1. Posture: engine version and parameter values.

aws rds describe-db-parameters --db-parameter-group-name pg18-pq \
  --query "Parameters[?ParameterName=='ssl_groups'].[ParameterValue]" --output text
psql "host=$H sslmode=verify-full sslrootcert=global-bundle.pem" -c "SHOW ssl_groups"

  1. Live test from a host with OpenSSL 3.5, for example a debian:trixie-slim task in the same VPC. PQ must succeed; classical must still work (fallback).

# PostgreSQL
openssl s_client -connect $H:5432 -starttls postgres -tls1_3 -groups X25519MLKEM768 -brief </dev/null
openssl s_client -connect $H:5432 -starttls postgres -groups X25519 -brief </dev/null
# MySQL / MariaDB
openssl s_client -connect $H:3306 -starttls mysql -groups X25519MLKEM768 -brief </dev/null
# Valkey / Redis (direct TLS)
openssl s_client -connect $H:6379 -groups X25519MLKEM768 -brief </dev/null

Expect Negotiated TLS1.3 group: X25519MLKEM768 for the PQ run and Peer Temp Key: X25519 for the classical one (Tested on every self-managed engine above).

  1. Observed signal on the server:

  • PostgreSQL: log_connections prints protocol, cipher and bits, not the group (Tested); pg_stat_ssl has no group column. Use the probe.

  • MySQL 26: SHOW SESSION STATUS LIKE 'Tls_key_exchange_algorithm' (Tested). Aurora MySQL: Aurora_ssl_named_group (Documented in the 3.14.0 notes).

  • Valkey, MariaDB: no server-side field; use the probe.

Pitfalls and rollback

  • Fallback is silent. A Debian 12 libpq client still connects to a PQ-first server using X25519 (Tested). Only enforcement (PQ-only groups, force_pqc) exposes it, by breaking it.

  • Server order is not always obeyed. With OpenSSL 3.5, a client that sent only an X25519 key share got X25519 although the server listed ML-KEM first (Tested on Valkey); OpenSSL avoids a HelloRetryRequest. Fix the client, or enforce.

  • Self-managed MySQL 8.4 and 9.x cannot be fixed with OpenSSL 3.5 alone; the server sticks to P-256 (Tested).

  • Official MariaDB images before 13 run on Ubuntu 24.04 with OpenSSL 3.0: no PQ (Tested).

  • RDS Proxy terminates TLS; that leg stays classical. Bypass it for sensitive data or record an exception.

  • ML-KEM needs TLS 1.3. Clients or servers pinned to TLS 1.2 stay classical.

  • Rollback: set ssl_groups back to prime256v1:X25519 (dynamic, new connections only), set force_pqc=OFF, or remove OPENSSL_CONF and restart. Existing sessions are not dropped.

Full configuration files

postgresql.conf (TLS section)

# /var/lib/postgresql/data/postgresql.conf  (PostgreSQL 18, OpenSSL 3.5) - TLS section
listen_addresses = '*'
ssl = on
ssl_cert_file = '/etc/postgresql/tls/server.crt'
ssl_key_file  = '/etc/postgresql/tls/server.key'        # mode 0600, owner postgres
ssl_ca_file   = '/etc/postgresql/tls/ca.crt'            # only for client-certificate auth
ssl_min_protocol_version = 'TLSv1.2'                    # 'TLSv1.3' to enforce PQ
ssl_groups = 'X25519MLKEM768:X25519:prime256v1'         # PQ-only: 'X25519MLKEM768'
log_connections = on

rds-pg-pq.tf (Terraform: RDS instance and Aurora cluster parameter groups)

# rds-pg-pq.tf - hybrid PQ key exchange for RDS for PostgreSQL 18 and Aurora PostgreSQL 18
variable "enforce_pq" {
  type    = bool
  default = false
}

locals {
  ssl_groups = var.enforce_pq ? "X25519MLKEM768,SecP256r1MLKEM768" : "X25519MLKEM768,SecP256r1MLKEM768,X25519,prime256v1"
  min_tls    = var.enforce_pq ? "TLSv1.3" : "TLSv1.2"
}

resource "aws_db_parameter_group" "pg18_pq" {
  name   = "pg18-pq"
  family = "postgres18"

  parameter {
    name         = "ssl_groups"
    value        = local.ssl_groups
    apply_method = "immediate"

  parameter {
    name         = "ssl_min_protocol_version"
    value        = local.min_tls
    apply_method = "immediate"

    apply_method = "immediate"
  }
