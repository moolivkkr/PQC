IoT devices

What decides PQ here

The device's TLS library decides the client side, and the broker decides the server side. On microcontrollers that library is the one compiled into the firmware: Mbed TLS (the FreeRTOS, ESP-IDF and Zephyr default) has no ML-KEM, while wolfSSL does. On Linux-class devices it is the system OpenSSL, or the s2n-tls + AWS-LC stack bundled inside the AWS CRT that the AWS IoT Device SDKs v2 use. On the server side, AWS IoT Core offers no PQ security policy, so device-to-IoT Core connections stay classical whatever the device offers. PQ is achievable today only on hops you control: a self-run broker (Mosquitto, EMQX, HiveMQ), a gateway's uplink to your own endpoints, or a PQ tunnel.

The plan therefore has three parts: ship PQ-capable stacks in new and updatable devices now, enforce PQ on brokers and gateways you run, and move IoT Core traffic when AWS adds a PQ policy. All tests on this tab ran on 2026-11-14 in local containers, without AWS access. Scripts and outputs are in the work directory deep/netiot/ (mosq/, wolf/).

Client side (devices)

Microcontrollers: wolfSSL, the only MCU path to ML-KEM today

  • Build: wolfSSL 5.9.1+ builds ML-KEM by default. For older 5.8.x builds or user_settings.h builds, define WOLFSSL_HAVE_MLKEM, WOLFSSL_SHA3, WOLFSSL_SHAKE128, WOLFSSL_SHAKE256, HAVE_CURVE25519, WOLFSSL_TLS13 and HAVE_SUPPORTED_CURVES. Drop the sizes you don't need with WOLFSSL_NO_ML_KEM_512 / WOLFSSL_NO_ML_KEM_1024. Documented (examples/configs/user_settings_pq.h). With configure, the flag is --enable-mlkem (Claimed, wolfSSL posts).

  • Code: after wolfSSL_new(), call wolfSSL_UseKeyShare(ssl, WOLFSSL_X25519MLKEM768) so the first ClientHello carries the hybrid share. This avoids a HelloRetryRequest. Set the order with wolfSSL_CTX_set_groups() / wolfSSL_set_groups(), and keep WOLFSSL_ECC_X25519 and WOLFSSL_ECC_SECP256R1 after the hybrid group for fallback. Constants in wolfssl/ssl.h: WOLFSSL_X25519MLKEM768 = 4588, WOLFSSL_SECP256R1MLKEM768 = 4587, WOLFSSL_SECP384R1MLKEM1024 = 4589. There is no WOLFSSL_X25519_ML_KEM_768.

  • FreeRTOS coreMQTT: transport_wolfSSL.c sets no groups, so the device gets the build's defaults. Add the two calls above in TLS_FreeRTOS_Connect after wolfSSL_new (patch under Full configuration files).

  • Memory: wolfSSL reports ML-KEM-768 at about 32 KB stack and 12 KB heap with the default code. With --enable-smallstack it is about 2 KB stack and 27 KB heap. These were measured on a Raspberry Pi 5, not an MCU (Claimed, wolfSSL blog). Size TLS task stacks and receive buffers for a ClientHello of about 1.3 KB and a ServerHello of about 1.2 KB.

  • Test (Tested, wolfSSL 5.9.4, Alpine 3.24 package with WOLFSSL_HAVE_MLKEM): pqclient.c reached a PQ-only OpenSSL 3.5 server with group=X25519MLKEM768, and a classical-only server with group=X25519. The classical-only variant was refused by the PQ-only server, as expected (3/3).

Microcontrollers: Mbed TLS, ESP-IDF, Zephyr

Mbed TLS and TF-PSA-Crypto have no ML-KEM as of Mbed TLS 4.2.0 (July 2026). Trusted Firmware's minutes put ML-DSA first and "then look into ML-KEM" (Claimed). ESP-IDF esp_tls_cfg_t.groups_list takes only Mbed TLS groups. For PQ on ESP32, switch to wolfSSL with CONFIG_ESP_TLS_CUSTOM_STACK / esp_tls_register_stack(), or use wolfSSL's ESP-IDF examples. Devices that talk only to AWS IoT Core gain nothing from PQ until IoT Core supports it.

Linux-class devices and gateways: OpenSSL 3.5 and Mosquitto clients

On Debian 13 or Alpine 3.24, mosquitto_pub and mosquitto_sub offer X25519MLKEM768 first with no options. Mosquitto has no groups option. To restrict or enforce the groups, set OPENSSL_CONF for the process. Tested: mosquitto_pub reached a PQ-only broker with defaults. With OPENSSL_CONF limited to X25519/P-256 it failed with Error: Protocol error. For AL2023, Yocto and Buildroot images, see Hosts and OS.

AWS IoT Device SDK v2 (Python, JavaScript, Java, C++) via the AWS CRT

On Linux the CRT uses aws-c-io → s2n-tls + AWS-LC, bundled in the wheel, npm package or jar. Current aws-c-io maps the default to a PQ s2n policy (AWS-CRT-SDK-TLSv1.0-2025-PQ) and PQ_DEFAULT to AWS-CRT-SDK-TLSv1.2-2025-PQ (Documented, aws-c-io source).

Greengrass v2, Android, OPC UA, LoRaWAN, cellular

  • Greengrass nucleus (Java): MQTT goes through aws-crt-java (0.45.0 in the current pom), so PQ is likely offered on Linux. This is inferred, not confirmed, and IoT Core is classical anyway. Component HTTPS calls follow the JDK (Java). Nucleus lite links the system OpenSSL, so use an OpenSSL 3.5 OS image (Debian 13, Alpine 3.24, or Yocto with OpenSSL 3.5).

  • Android gateways: whether Conscrypt has X25519MLKEM768 on by default per Android version is not confirmed; see Mobile, desktop and CLI clients.

  • OPC UA: no PQ SecurityPolicy exists (OPC 10000-2, 1.05.06). Over untrusted links, carry OPC UA in a PQ tunnel: strongSwan 6.0.2+ IPsec or a PQ TLS proxy (Network devices and egress).

  • LoRaWAN: AES-128 session keys and no public-key handshake, so ML-KEM doesn't apply on the radio link. The network server's cloud backhaul is ordinary TLS; treat it like a Linux gateway. No LoRa Alliance PQ statement found.

  • Cellular: 3GPP's PQ transition study is TR 33.703 (Release 20). There is no ML-KEM in 5G NAS/AS yet, so protect the IP payload with TLS or IPsec on top.

Pitfalls and rollback

  • IoT Core is classical: don't hold device rollout back waiting for PQ on IoT Core. Ship PQ-capable stacks now, and enforce PQ on your own brokers and gateways first. Watch the IoT Core security policies page for a PQ policy. Device lifetimes of 10 years or more make procurement the cheapest point to fix this.

  • Buffers and stacks: a hybrid ClientHello is about 1.3 KB and the ServerHello about 1.2 KB. MCU TLS receive buffers of 1–2 KB, MQTT_NETWORK_BUFFER_SIZE and task stacks need headroom. Test on real hardware for heap fragmentation, handshake time and battery cost.

  • HelloRetryRequest: if the device lists the hybrid group but sends only an X25519 share, a PQ-only server forces an extra round trip. Send the hybrid key share first (wolfSSL_UseKeyShare).

  • PKCS#11 and secure-element keys: the CRT path gives no TLS 1.3 and so no PQ there. The alternative is wolfSSL with a crypto callback for the secure element.

  • Stale names: PQ_TLSv1_0_2021_05 (awscrt) and the Kyber IDs such as WOLFSSL_P521_KYBER_LEVEL5 are pre-standard, and servers no longer accept them. Replace them.

  • ESP-IDF registry lag: the managed wolfSSL component is 5.8.2, older than default-on ML-KEM. Pin a newer wolfSSL, or enable ML-KEM in user_settings.h, and test.

  • Rollback: brokers: remove the OPENSSL_CONF drop-in to return to hybrid-preferred with classical fallback. Devices: keep X25519/P-256 after the hybrid group so that fallback needs no change, and ship an OTA config flag that skips wolfSSL_UseKeyShare if a model misbehaves.

pqclient.c (Tested, wolfSSL 5.9.4 on Alpine 3.24 against OpenSSL 3.5 servers. Build: cc pqclient.c -lwolfssl -o pqclient)

/* pqclient.c - wolfSSL TLS 1.3 client offering X25519MLKEM768 (hybrid) first.
 * Run: ./pqclient HOST PORT CAFILE [classic] */
#include <wolfssl/options.h>
#include <wolfssl/ssl.h>
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <netdb.h>
#include <sys/socket.h>
#include <unistd.h>

int main(int argc, char **argv) {
    if (argc < 4) { fprintf(stderr, "usage: %s host port ca [classic]\n", argv[0]); return 2; }
    int classic = argc > 4 && strcmp(argv[4], "classic") == 0;
    struct addrinfo hints = {0}, *ai; hints.ai_socktype = SOCK_STREAM;
    if (getaddrinfo(argv[1], argv[2], &hints, &ai) != 0) return 2;
    int fd = socket(ai->ai_family, SOCK_STREAM, 0);
    if (connect(fd, ai->ai_addr, ai->ai_addrlen) != 0) { perror("connect"); return 2; }

    wolfSSL_Init();
    WOLFSSL_CTX *ctx = wolfSSL_CTX_new(wolfTLSv1_3_client_method());
    wolfSSL_CTX_load_verify_locations(ctx, argv[3], NULL);
    /* Supported groups, in preference order. */
    int pq[] = { WOLFSSL_X25519MLKEM768, WOLFSSL_ECC_X25519, WOLFSSL_ECC_SECP256R1 };
    int cl[] = { WOLFSSL_ECC_X25519, WOLFSSL_ECC_SECP256R1 };
    if (wolfSSL_CTX_set_groups(ctx, classic ? cl : pq, classic ? 2 : 3) != WOLFSSL_SUCCESS)
        fprintf(stderr, "set_groups failed\n");
    WOLFSSL *ssl = wolfSSL_new(ctx);
    /* Key share sent in the first ClientHello (avoids a HelloRetryRequest round trip). */
    wolfSSL_UseKeyShare(ssl, classic ? WOLFSSL_ECC_X25519 : WOLFSSL_X25519MLKEM768);
    wolfSSL_UseSNI(ssl, WOLFSSL_SNI_HOST_NAME, argv[1], strlen(argv[1]));
    wolfSSL_set_fd(ssl, fd);
    if (wolfSSL_connect(ssl) != WOLFSSL_SUCCESS) {
        char e[80]; printf("HANDSHAKE_FAIL %s\n", wolfSSL_ERR_error_string(wolfSSL_get_error(ssl, 0), e));
        return 1;
    }
    printf("HANDSHAKE_OK version=%s group=%s\n", wolfSSL_get_version(ssl), wolfSSL_get_curve_name(ssl));
    wolfSSL_shutdown(ssl); wolfSSL_free(ssl); wolfSSL_CTX_free(ctx); close(fd);
    return 0;
}

Output: HANDSHAKE_OK version=TLSv1.3 group=X25519MLKEM768 (PQ-only server), HANDSHAKE_OK version=TLSv1.3 group=X25519 (classical-only server), and HANDSHAKE_FAIL received alert fatal error for the classic variant against the PQ-only server.

crt_mqtt_pq.py (Tested, awscrt 0.36.1 / awsiotsdk 1.31.0. Usage: python crt_mqtt_pq.py HOST PORT CA CERT KEY [PQ_DEFAULT|DEFAULT|TLSv1_2_2025_07])

"""MQTT over mutual TLS with the AWS CRT (aws-iot-device-sdk-python-v2 / awscrt).
On Linux, awscrt uses s2n-tls + AWS-LC; cipher_pref selects the s2n security policy."""
import sys
from awscrt import io, mqtt

host, port, ca, cert, key = sys.argv[1:6]
pref_name = sys.argv[6] if len(sys.argv) > 6 else "PQ_DEFAULT"

opts = io.TlsContextOptions.create_client_with_mtls_from_path(cert, key)
opts.override_default_trust_store_from_path(None, ca)
opts.cipher_pref = getattr(io.TlsCipherPref, pref_name)   # PQ_DEFAULT = hybrid ML-KEM offered
tls_ctx = io.ClientTlsContext(opts)

elg = io.EventLoopGroup(1)
resolver = io.DefaultHostResolver(elg)
bootstrap = io.ClientBootstrap(elg, resolver)
client = mqtt.Client(bootstrap, tls_ctx)
conn = mqtt.Connection(client=client, host_name=host, port=int(port),
                       client_id=f"crt-{pref_name}", clean_session=True, keep_alive_secs=30)
try:
    conn.connect().result(timeout=15)
    pub, _ = conn.publish(topic="pq/test", payload=b"hello", qos=mqtt.QoS.AT_LEAST_ONCE)
    pub.result(timeout=10)
    conn.disconnect().result(timeout=10)
    print(f"CONNECT_OK pref={pref_name}")
except Exception as e:  # noqa: BLE001
    print(f"CONNECT_FAIL pref={pref_name}: {type(e).__name__}: {e}")
