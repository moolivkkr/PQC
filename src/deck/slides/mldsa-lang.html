KEY MESSAGE: ML-DSA works today only for OpenSSL 3.5 clients, and on AL2023 only with one extra line, so dual certificates are the only safe way to serve it. • Python, Node.js and .NET on an OpenSSL 3.5 base pick the ML-DSA certificate and verify it. • On AL2023, which is our Lambda and much of our EC2 base, the crypto policy leaves ML-DSA out. Our ML-KEM config file doesn’t change that; the ML-DSA config file adds the signature algorithms, and then all three targets work. We found this in testing today. • OpenSSL 3.0, Go and Java get the ECDSA certificate from a dual server. Go and Java can verify ML-DSA chains but their TLS stacks don’t negotiate ML-DSA. • So a server that only has an ML-DSA certificate breaks Go, Java, OpenSSL 3.0 and default AL2023 clients. • The full e2e run per language and compute type is in progress; the ML-DSA client certificate column fills in from it.
