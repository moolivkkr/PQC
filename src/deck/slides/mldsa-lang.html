KEY MESSAGE: Only OpenSSL 3.5 stacks with ML-DSA enabled can use an ML-DSA certificate today, so dual certificates are the only safe way to serve it, and they break nobody. • The e2e run put 409 client cases against three ML-DSA servers. 91 used ML-DSA everywhere, 4 on two of three, and 307 got the ECDSA certificate from the dual server. • Node 22.20 and 24.5 and later bundle OpenSSL 3.5 and use ML-DSA everywhere, including Lambda, with or without our fix. • On AL2023 the default crypto policy leaves ML-DSA out, and our ML-KEM config file keeps that list. DEFAULT:PQ or the new ML-DSA config file turns it on. That’s the finding from this round. • .NET 8 can verify ML-DSA servers but can’t load an ML-DSA private key, so ML-DSA client certificates need .NET 10. • A surprise: Lambda Python 3.9 to 3.11 with our shim use ML-DSA, because pyOpenSSL’s wheel bundles OpenSSL 3.5. • Go and Java verify ML-DSA chains but their TLS stacks don’t negotiate it, so they get ECDSA. • Most important: every client that connects at all connected to the dual server with the extra ML-DSA root in its bundle, including OpenSSL 1.0.2 and Java 8.
