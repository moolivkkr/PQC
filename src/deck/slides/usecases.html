Post-quantum TLS on AWS · 05 · Guide: Use cases; vendor sources checked 2026-11-16

KEY MESSAGE: Key exchange and certificates are two separate jobs. ML-KEM protects every connection now; ML-DSA is urgent only where a signature must be trusted for years. • ML-KEM stops harvest-now-decrypt-later. It needs no new certificates, works in every language we tested, and is the rollout. • ML-DSA protects against forged signatures, which only matters once a quantum computer exists. So it’s urgent only for things trusted for a decade: device roots in firmware and code or firmware signing. • Public HTTPS can’t use ML-DSA today: AWS’s certificate and load balancer services don’t serve it, and browsers don’t negotiate it. Chrome is heading to Merkle Tree Certificates instead. • Internal HTTPS and workload identity can pilot it with dual certificates from AWS Private CA; IAM Roles Anywhere already accepts ML-DSA. • User certificates: Microsoft AD CS issues ML-DSA, but Microsoft itself calls Schannel support a pilot. • SSH: key exchange is already PQ with OpenSSH 10; hybrid ML-DSA keys arrived in OpenSSH 10.6 in October. • Hybrid certificates in TLS mean two certificates today; the one-certificate composite form isn’t negotiable yet. • Sources: AWS, Microsoft, OpenSSH release notes, IETF; Public HTTPS, user and IoT rows are documented, not tested here.
