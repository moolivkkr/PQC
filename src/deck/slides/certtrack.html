When stacks catch up

Go, Java, public HTTPS

Go and Java verify ML-DSA but don’t negotiate it; ACM, ALB and browsers don’t serve it. Recheck each quarter.

Never ML-DSA alone while any client runs Go, Java, OpenSSL 3.0 or default AL2023: they fail the handshake. On AL2023, ML-DSA needs DEFAULT:PQ or the new openssl-pq-mldsa.cnf; our ML-KEM file alone isn’t enough (found in e2e). Chains grow from 0.9 KB to 11.8 KB.

Post-quantum TLS on AWS · 23 · e2e targets mldsa-dual, mldsa-only, mldsa-mtls; guide: Certificates (ML-DSA)

KEY MESSAGE: Certificates move on their own track: distribute ML-DSA roots and sign long-lived artifacts now, pilot dual certificates internally next year, and wait for AWS and browsers before touching public HTTPS. • Step one costs almost nothing: an ML-DSA test root from Private CA added to our trust bundles. The e2e run showed old clients ignore the root they can’t read. • Firmware and artifacts that are verified for years get an ML-DSA signature next to the existing one, from KMS. • The pilot is one internal service with two certificates: ECDSA for everyone, ML-DSA for clients that ask for it. IAM Roles Anywhere can take an ML-DSA trust anchor. • The rule: never serve ML-DSA alone yet. Go and Java verify it but don’t negotiate it, OpenSSL 3.0 can’t, and AL2023 needs an extra line we found in testing. • The cost is size: a certificate chain goes from under 1 KB to about 12 KB, which matters for constrained devices and high-volume handshakes. • Public HTTPS waits for ACM, the load balancers and browsers.
