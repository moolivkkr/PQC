# PQ hybrid key exchange in IoT TLS stacks — verified facts (2026-11-14)

Labels: **Documented** = vendor docs/source/release notes opened; **Claimed** = vendor blog/forum/3rd-party; **Not found** = searched, no source. "not confirmed" = unsure.

Standard: **RFC 10024** (Aug 2026, Proposed Standard) "PQ/T Hybrid Key Agreement Mechanisms for TLS 1.3": X25519MLKEM768 = 4588 (0x11EC), SecP256r1MLKEM768 = 4587 (0x11EB), SecP384r1MLKEM1024 = 4589 (0x11ED). X25519MLKEM768 client share 1216 B (1184+32), server share 1120 B. Documented — https://www.rfc-editor.org/rfc/rfc10024.html

## 1. wolfSSL — PQ: YES
- ChangeLog (https://raw.githubusercontent.com/wolfSSL/wolfssl/master/ChangeLog.md), Documented:
  - 5.7.0 (2024-03-20): Kyber experimental, `--enable-experimental --enable-kyber`.
  - 5.7.4 (2024-10-24): Kyber/ML-DSA "Update to final specification".
  - 5.8.0 (2025-04-24): "Add more PQC hybrid key exchange algorithms such as support for combinations with X25519 and X448" (PR 7821); "Update Kyber APIs to ML-KEM APIs" (PR 8536). Exact release that added the 4588 constant: not confirmed (5.8.0 is the likely one; not verified).
  - 5.8.2 (2025-07-17): "Backward compatibility has been implemented for ML_KEM IDs" (PR 8827) — old IDs only with `WOLFSSL_ML_KEM_USE_OLD_IDS` (blog https://www.wolfssl.com/?p=46840).
  - 5.9.1 (2026-04-08): "Enabled PQC algorithm ML-KEM (FIPS203) on by default." (PR 9732). Release blog https://www.wolfssl.com/?p=47549.
  - 5.9.2 (2026-06-23): liboqs ML-KEM/ML-DSA integration removed (native only); `WOLFSSL_MLKEM_DYNAMIC_KEYS`; `WOLFSSL_KEY_SHARE_DEFAULT_GROUP` decouples speculative ClientHello key share from `preferredGroup[0]` (PR 10435). CVE-2026-7531 (UAF in PQC hybrid key-share), CVE-2026-10097 (AVX2 ML-KEM-1024 decap compare).
  - 5.9.4 (2026-09-25): PQ-only TLS 1.3 builds; `wolfSSL_set1_groups_list()` accepts "MLKEMxxx aliases", case-insensitive (PR 10686); DTLS fragmented CH "default only in ML-KEM builds".
- Constants, `wolfssl/ssl.h` (master), Documented: `WOLFSSL_ML_KEM_512 = 512`, `WOLFSSL_ML_KEM_768 = 513`, `WOLFSSL_ML_KEM_1024 = 514`, `WOLFSSL_SECP256R1MLKEM768 = 4587`, `WOLFSSL_X25519MLKEM768 = 4588`, `WOLFSSL_SECP384R1MLKEM1024 = 4589`, plus non-IANA-final `WOLFSSL_SECP256R1MLKEM512 = 12107`, `WOLFSSL_SECP384R1MLKEM768 = 12108`, `WOLFSSL_SECP521R1MLKEM1024 = 12109`, `WOLFSSL_X25519MLKEM512 = 12214`, `WOLFSSL_X448MLKEM768 = 12215`. (`WOLFSSL_X25519_ML_KEM_768` does NOT exist.) `WOLFSSL_MAX_GROUP_COUNT` 36 with `WOLFSSL_HAVE_MLKEM`, else 10.
- API (ssl.h), Documented: `int wolfSSL_UseKeyShare(WOLFSSL* ssl, word16 group);` (TLS13) — e.g. `wolfSSL_UseKeyShare(ssl, WOLFSSL_X25519MLKEM768);`; `int wolfSSL_CTX_set_groups(WOLFSSL_CTX* ctx, int* groups, int count);`; `wolfSSL_set_groups(...)`; `wolfSSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:...")` (needs `OPENSSL_EXTRA` + `HAVE_SUPPORTED_CURVES`).
- Configure: `--enable-mlkem` (Claimed: wolfSSL curl/wolfTPM posts); size variants `--enable-mlkem=all,512,small` (Documented in wolfSSL memory blog). `--enable-tls-mlkem-standalone`: **Not found**. INSTALL §15 still shows legacy `./configure --enable-kyber --enable-dilithium`, test with `./examples/server/server -v 4 --pqc SecP384r1MLKEM1024` (Documented, https://raw.githubusercontent.com/wolfSSL/wolfssl/master/INSTALL).
- user_settings.h (examples/configs/user_settings_pq.h, Documented): `#define WOLFSSL_TLS13`, `HAVE_SUPPORTED_CURVES`, `WOLFSSL_HAVE_MLKEM`, `WOLFSSL_SHAKE128`, `WOLFSSL_SHAKE256`, `WOLFSSL_SHA3`, `HAVE_CURVE25519`; drop sets with `WOLFSSL_NO_ML_KEM_512/_768/_1024`. `WOLFSSL_WC_MLKEM` (native impl) — Claimed (3rd-party crate/forum); moot after 5.9.2 removed liboqs.
- Default key share in 5.8.x: ML-KEM not default-on in 5.8.x (default-on only from 5.9.1) → hybrid not offered by default in a stock 5.8.x build (inference from changelog). 5.9.2+: PR 10435 says default speculative share "prefers widely deployed groups (PQ/T hybrids with X25519 or SECP256R1" — exact group/macro value not confirmed. Claimed/PR text: https://github.com/wolfSSL/wolfssl/pull/10435. Verify on target with a packet capture.
- Memory (wolfSSL blog 2025-07/08, Raspberry Pi 5 testwolfcrypt, NOT MCU), ML-KEM-768: small code: stack 32,672 / heap 11,968 B; + `-DWOLFSSL_MLKEM_ENCAPSULATE_SMALL_MEM -DWOLFSSL_MLKEM_MAKEKEY_SMALL_MEM`: stack 32,928 / heap 5,824; + `--enable-smallstack`: stack 2,112 / heap 27,306. Claimed (vendor blog) https://www.wolfssl.com/optimizing-post-quantum-algorithm-memory-usage-on-embedded-systems/ . ESP32 Kyber demo (2024): server task "minimum stack size of approximately 10K bytes" https://www.wolfssl.com/post-quantum-key-share-on-the-espressif-esp32/ . Cortex-M figures: Not found.
- ESP-IDF managed component `wolfssl/wolfssl`: latest on registry 5.8.2~1 (wolfSSL 5.8.2, 2025-07-17) — i.e. pre-default-on ML-KEM. No ML-KEM Kconfig found. Documented https://components.espressif.com/components/wolfssl/wolfssl . 2024 ESP32 demo defines: `WOLFSSL_EXPERIMENTAL_SETTINGS`, `WOLFSSL_HAVE_KYBER`, `WOLFSSL_WC_KYBER`, `WOLFSSL_SHA3`, `wolfSSL_UseKeyShare(ssl, WOLFSSL_P521_KYBER_LEVEL5)` (obsolete names).
- FreeRTOS coreMQTT wolfSSL transport (`FreeRTOS-Plus/.../network_transport/transport_wolfSSL.c`): `wolfSSL_CTX_new( wolfSSLv23_client_method_ex( NULL ) )`; no `wolfSSL_UseKeyShare`/groups call → whatever the wolfSSL build defaults are. Documented (source) https://raw.githubusercontent.com/FreeRTOS/FreeRTOS/main/FreeRTOS-Plus/Source/Application-Protocols/network_transport/transport_wolfSSL.c . To force hybrid, add `wolfSSL_UseKeyShare(ssl, WOLFSSL_X25519MLKEM768)` after `wolfSSL_new`.

## 2. Mbed TLS / TF-PSA-Crypto — PQ in TLS: NO

TF-PSA-Crypto 1.0.0/1.1.0/1.2.0 ChangeLog: no ML-KEM/ML-DSA entries. Documented https://raw.githubusercontent.com/Mbed-TLS/mbedtls/development/ChangeLog , https://raw.githubusercontent.com/Mbed-TLS/TF-PSA-Crypto/development/ChangeLog
- Roadmap: TF TSC minutes 2026-02-19: ML-DSA first (mldsa-native via PSA driver, ML-DSA-87 only), PSA API ~end Q2 2026; "After ML-DSA … look into ML-KEM". Claimed (minutes) https://lists.trustedfirmware.org/archives/list/tsc@lists.trustedfirmware.org/thread/3PMZIZ25FQOI6WY4L4VTMCEFWH3HNFWI/

## 4. s2n-tls / aws-c-io / awscrt — PQ: YES, and DEFAULT ON in current aws-c-io
- s2n-tls usage guide ch16 (Documented, https://aws.github.io/s2n-tls/usage-guide/ch16-post-quantum.html): `"default_pq"` = PQ counterpart of `"default_tls13"`, pinned `"20250721"`, offers x25519+mlkem768, secp256r1+mlkem768, secp384r1+mlkem1024; "s2n-tls must be built with aws-lc to use post-quantum algorithms"; also `cnsa_2`, `cnsa_1_2_interop`; check with `s2n_connection_get_kem_group_name()`. ch06: `"default"`=20251014, `"default_tls13"`=20240503, `"default_fips"`=20251015 — groups listed only secp256r1/secp384r1/x25519 → plain s2n "default"/"default_tls13" are NOT PQ. Policy name "PQ-TLS-1-2-2024-10-08": Not found.
- aws-c-io `include/aws/io/tls_channel_handler.h` (main, Documented): `AWS_IO_TLS_CIPHER_PREF_PQ_TLSv1_0_2021_05 = 6` marked `/* Deprecated */` (also KMS_PQ_* 1–5); `AWS_IO_TLS_CIPHER_PREF_PQ_TLSV1_2_2024_10 = 7`; `AWS_IO_TLS_CIPHER_PREF_PQ_DEFAULT = 8` ("Recommended default policy with post-quantum algorithm support. - aws-c-io `source/s2n/s2n_tls_channel_handler.c` (main, Documented) mapping: PQ_DEFAULT → `"AWS-CRT-SDK-TLSv1.2-2025-PQ"`; PQ_TLSV1_2_2024_10 → `"AWS-CRT-SDK-TLSv1.2-2023-PQ"`; TLSV1_2_2025_07 → `"AWS-CRT-SDK-TLSv1.2-2025"`; TLSV1_0_2023_06 and NON_PQ_DEFAULT → `"AWS-CRT-SDK-TLSv1.0-2023"`; SYSTEM_DEFAULT → keep min-version policy: TLSv1_2 → `"AWS-CRT-SDK-TLSv1.2-2025-PQ"`, TLSv1_3 → `"AWS-CRT-SDK-TLSv1.3-2025-PQ"`, SYS_DEFAULTS → `"AWS-CRT-SDK-TLSv1.0-2025-PQ"`. PQ_TLSv1_0_2021_05 no longer in supported list (→ `AWS_IO_TLS_CIPHER_PREF_UNSUPPORTED`).
- **Caveat (Documented, same file):** when a custom key-op handler is used (PKCS#11/HSM/TPM private key), min-version maps to legacy ELB policies (`"ELBSecurityPolicy-TLS-1-1-2017-01"` default, `"ELBSecurityPolicy-TLS-1-2-Ext-2018-06"`), TLS 1.3 + PKCS#11 errors "TLS 1.3 with PKCS#11 is not supported yet." → **no PQ for PKCS#11 devices** unless an explicit cipher_pref overrides (the later cipher_pref switch does override `security_policy`; PQ needs TLS 1.3 so not confirmed it works with PKCS#11).
- First aws-c-io release with PQ-by-default: not confirmed (GitHub releases page notes don't mention it).
- Platforms: s2n path is Linux/Unix (non-Apple) only; macOS/iOS use Apple Secure Transport/Network.framework, Windows uses SChannel — PQ there depends on the OS (inference from aws-c-io source layout; not separately verified).
- awscrt Python `awscrt/io.py` (main, Documented): `TlsCipherPref.DEFAULT = 0`, `PQ_TLSv1_0_2021_05 = 6` (Kyber Round 3 docstring still present), `PQ_DEFAULT = 8`, `TLSv1_2_2025_07 = 9`; `TlsContextOptions.cipher_pref` (default `TlsCipherPref.DEFAULT`), `min_tls_ver`; `TlsCipherPref.is_supported()`. ## Runbook bottom line
- Device→AWS IoT Core: **no PQ today** (no PQ IoTSecurityPolicy). Client-side hybrid offers are harmless (falls back to x25519/P-256) but cost ~1.2 KB extra ClientHello.
- Linux CRT SDKs (Device SDK v2 via aws-c-io main) already default to `AWS-CRT-SDK-*-2025-PQ`; opt out with `NON_PQ_DEFAULT` (C) — except PKCS#11/custom-key path which uses non-PQ ELB policies.
- Self-hosted brokers: Mosquitto/OpenSSL ≥3.5 hybrid by default; EMQX depends on OTP ssl ≥11.5 (preferred from 11.7); HiveMQ needs JDK 27.
- MCUs: only wolfSSL gives ML-KEM TLS (default-on from 5.9.1, but ESP registry still 5.8.2); Mbed TLS/TF-PSA-Crypto have none through 4.2.0/1.2.0.
