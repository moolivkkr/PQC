## 1. H1 and lead paragraphs
H1: Network devices, VPN and egress

A network device sets PQ only where it terminates TLS or IKE itself. A decrypting firewall, ADC or proxy runs two separate handshakes: the client leg (client to device, where the device acts as the server) and the server leg (device to origin, where the device acts as the client). Each leg gets PQ only if that device's TLS stack and profile offer ML-KEM. A device that doesn't decrypt passes the client's handshake through unchanged, so PQ then depends on the two endpoints. It only has to forward the roughly 1.2 KB larger ClientHello without dropping it. For IPsec, both IKEv2 peers must support RFC 9370 additional key exchanges with ML-KEM.

Network devices play two roles here: sensors that show which connections are classical, and converters that terminate classical TLS and re-originate PQ TLS for clients you can't upgrade. All tests on this tab ran on 2026-11-14 in local containers, without AWS access. Scripts and outputs are in the work directory deep/netiot/ (squid/, swan/, zeek/, envoy/).
