## 1. H1 and lead paragraphs
H1: Certificates and signatures (ML-DSA)

ML-DSA (FIPS 204) replaces the signatures in certificates; it is the second step after ML-KEM key exchange. It is less urgent: recorded traffic can be decrypted later, but a signature only has to hold at the moment of the handshake. Today ML-DSA works in private PKI only.

Three parties decide whether a handshake uses an ML-DSA certificate. The CA must sign with ML-DSA. The server must hold an ML-DSA certificate and a TLS library that can sign with it (OpenSSL 3.5+). The client must offer ML-DSA in its signature_algorithms extension and be able to verify the chain. A server that also holds an ECDSA certificate falls back to it for clients that don't offer ML-DSA; that dual-certificate setup is the safe way to start (Tested 2026-11-14).

## 3. Status matrix (first table)
| Service | ML-DSA | Evidence |
| AWS Private CA | CA and end-entity certificates. KeyAlgorithm and SigningAlgorithm ML_DSA_44, ML_DSA_65, ML_DSA_87 (the same value in both). All commercial, GovCloud and China regions since November 2025. | Documented (algorithms, API) |
| AWS KMS | Signing keys ML_DSA_44/65/87, algorithm ML_DSA_SHAKE_256; RAW messages up to 4 KB, EXTERNAL_MU for larger | Documented (KMS ML-DSA) |
| IAM Roles Anywhere | ML-DSA trust anchors and end-entity certificates (March 2026) | Documented |
| ACM public certificates; ALB, NLB, CloudFront, API Gateway listeners | RSA and ECDSA only; cannot serve ML-DSA | Claimed (third-party report) |
| ACM private certificates (from Private CA) | ACM supports "some but not all" Private CA algorithms; ML-DSA through ACM not confirmed | Documented (the caveat); ML-DSA Unverified |
| AWS CloudHSM | AWS's PQC migration page lists ML-DSA as preview; GA not confirmed | Unverified |
| Public web PKI and browsers | No public CA issues ML-DSA; browsers don't accept it; Chrome is pursuing Merkle Tree Certificates | Claimed |
