
[mttvddjsrgd.0 H1] PQC Detection and Remediation by Language and Compute
[.68 H2] Summary {.76} Outbound TLS becomes post-quantum (PQ) only when the client's TLS library offers the hybrid group X25519MLKEM768 in TLS 1.3. Whether it does depends on the language runtime and its crypto library, not on the compute type. Compute type decides two other things: how you can see non-PQ connections, and how the fix ships.

 {.398} **Detection** differs by compute type. Lambda and Fargate cannot be packet-mirrored, so they rely on AWS logs and app-side telemetry. Containers on EC2 can also use passive sensors.
 {.577} **Remediation** differs by language and version. Some need only a config file, some a Java agent or library shim, and some a runtime or toolchain upgrade.
 {.729} **Every change ships through build, package and release.** Configuration changes are released like code here, so the fix rides a shared build template, not per-function edits. {.901} How to read the evidence labels in the tables:

[.1264 H2] Detection: finding non-PQ connections {.1302} Use two kinds of signal together: **posture** (what a workload will negotiate, predicted from its runtime, versions and config) and **observed** (what a handshake actually negotiated, from logs or sensors). Posture covers everything you can inventory, including Lambda and Fargate, which can't be packet-mirrored. Observed signals confirm the fix and catch what posture misses, such as libraries that pin their own groups.

[.7407 H3] Python and .NET (system OpenSSL) {.7440} Both use the operating system's OpenSSL, so one config file serves both. It loads the AL2023 crypto policy and replaces only the group list:

 {.8019} **Set:** `OPENSSL_CONF=/var/task/pq-tls/openssl-pq.cnf`.
 {.8071} **Baseline check:** with this file, Python 3.12's minimum TLS version, cipher list and options were identical to the default. `OPENSSL_CONF=/dev/null` also enables PQ but drops the crypto policy and changed the cipher list, so don't use it.
 {.8307} **Python 3.9 to 3.11 on Lambda** (AL2, OpenSSL 1.1.1): a `sitecustomize.py` shim patches urllib3 and botocore to use pyOpenSSL, whose bundled OpenSSL offers PQ. Set `PYTHONPATH` to the shim's directory. It covers `requests` and `boto3`, not `ssl`, `http.client`, aiohttp or httpx. It overrides a deliberate botocore choice and was tested with certificate verification off, so treat it as a bridge until the runtime upgrade.

 {.9241} **Set:** `OPENSSL_CONF=/var/task/pq-tls/openssl-pq-node.cnf`.
 {.9298} **Watch for drift:** this file replaces AWS's rather than including it. Add a pipeline check that diffs AWS's file against ours, minus the PQ group.

[.9522 H3] Java (JSSE, independent of the OS) {.9557} Java's TLS stack doesn't use OpenSSL, so moving to AL2023 changes nothing for Java. JDKs before 25 have no ML-KEM groups.

 {.9681} **Java 8 to 21:** a Java agent (`pq-tls-agent.jar`, compiled for Java 8) registers Bouncy Castle 1.87 as the first JSSE provider and sets `jdk.tls.namedGroups=X25519MLKEM768,x25519,secp256r1,secp384r1` unless already set. Set `JAVA_TOOL_OPTIONS=-javaagent:/var/task/``pq-tls``/pq-tls-agent.jar`.
 {.9961} **Java 8 only:** also add `-Djdk.tls.client.protocols=TLSv1.3,TLSv1.2`, since its client defaults to TLS 1.2.
 {.10066} **Why an agent:** the Lambda Java bootstrap's system classpath is `/var/runtime/lib` only, so providers registered through `java.security` from other paths are silently ignored.
 {.10237} **Risk:** Bouncy Castle becomes the TLS provider for the whole process. Test functions that use custom keystores, FIPS mode or mutual TLS first.
 {.10379} **Java 25:** Corretto 25.0.5 negotiates PQ with the stock SunJSSE provider.
[.10451 H3] Go (own TLS stack)

 {.10472} **Needs both:** a Go 1.24+ toolchain and a `go` directive of 1.24+ in `go.mod`. A 1.25 build of a module whose `go.mod` says 1.23 stayed classical in testing.
 {.10622} **No-code override:** `GODEBUG=tlsmlkem=1` turned that build PQ, and can be set in the deployment config.
 {.10723} **Pitfall:** code that sets `tls.Config.CurvePreferences` gets no PQ.
[.10787 H3] Rust {.10792} rustls with the aws-lc-rs provider supports X25519MLKEM768. Sources disagree on which 0.23.x release made it the default (0.23.22 or 0.23.27). The AWS SDK for Rust defaults to PQ for crates published after 2025-08-29. Rebuild with current crates; apps on the `openssl` crate follow the system OpenSSL instead.
[.11100 H2] Inbound: front doors and TLS 1.3 enforcement {.11145} Inbound connections become PQ when the front door's TLS policy offers ML-KEM and the caller supports it. Allow TLS 1.2 and 1.3 first, measure, then move each endpoint to TLS 1.3 only once its TLS 1.2 traffic reaches zero. TLS negotiation already picks 1.3 when both sides support it, and TLS 1.3's downgrade protection stops an attacker forcing 1.2.

[.12898 H2] Rollout through build, package and release {.12941} Every change, including configuration, ships as a release here. So the fix lives in the shared build template, and each workload picks it up on its next release with no per-service code edits. {.13135} The release step is the only one that changes a workload; the others are automation around it.

 {.13232} **Classify.** The posture inventory sorts each workload into a matrix row and records the gap.
 {.13324} **Change request.** A bot opens a pull request in each repo that bumps the shared module or template. The template ships the right files under `/var/task/pq-tls/` (config file, agent jar or shim) and sets the matching variable. It leaves a workload's own `OPENSSL_CONF` alone and flags it for review. Bundling into the package avoids Lambda's 5-layer limit.
 {.13675} **Release.** The normal pipeline builds, packages and releases. A guardrail (cfn-guard, OPA/conftest or a CloudFormation Hook) warns, then later fails, on Lambda and task definitions missing the PQ settings, and on non-PQ ELB policies.
 {.13908} **Verify.** Observed signals confirm the workload's connections moved to PQ; shipping isn't proof. CLM tracks each workload as a campaign item. {.14048} Dormant workloads with no release coming: rank them by observed classical traffic. One making no classical outbound TLS doesn't need forcing; the rest get a no-op rebuild and release. Runtimes past AWS's block-update date can't be changed at all, so schedule those first.
