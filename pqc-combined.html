Overview

Summary

Outbound TLS becomes post-quantum (PQ) only when the client's TLS library offers the hybrid group X25519MLKEM768 in TLS 1.3. Whether it does depends on the language runtime and its crypto library, not on the compute type. Compute type decides two other things: how you can see non-PQ connections, and how the fix ships.

  • Detection differs by compute type. Lambda and Fargate cannot be packet-mirrored, so they rely on AWS logs and app-side telemetry. Containers on EC2 can also use passive sensors.

  • Remediation differs by language and version. Some need only a config file, some a Java agent or library shim, and some a runtime or toolchain upgrade.

  • Every change ships through build, package and release. Configuration changes are released like code here, so the fix rides a shared build template, not per-function edits.

Detection: finding non-PQ connections

Use two kinds of signal together: posture (what a workload will negotiate, predicted from its runtime, versions and config) and observed (what a handshake actually negotiated, from logs or sensors). Posture covers everything you can inventory, including Lambda and Fargate, which can't be packet-mirrored. Observed signals confirm the fix and catch what posture misses, such as libraries that pin their own groups.

Per-language detail

Each entry gives the exact setting, what it covers, and how to check it worked. All Lambda results come from the AL2023.12.20261109 base images.

Python and .NET (system OpenSSL)

Both use the operating system's OpenSSL, so one config file serves both. It loads the AL2023 crypto policy and replaces only the group list:

openssl_conf = openssl_init
.include /etc/pki/tls/openssl.d
[openssl_init]
providers = provider_sect
ssl_conf = ssl_module
[provider_sect]
default = default_sect
[default_sect]
activate = 1
[ssl_module]
system_default = pq_system_default
[pq_system_default]
.include = /etc/crypto-policies/back-ends/opensslcnf.config
Groups = *X25519MLKEM768:*X25519:secp256r1:X448:secp521r1:secp384r1:ffdhe2048:ffdhe3072:ffdhe4096:ffdhe6144:ffdhe8192

  • Set: OPENSSL_CONF=/var/task/pq-tls/openssl-pq.cnf.

  • Baseline check: with this file, Python 3.12's minimum TLS version, cipher list and options were identical to the default. OPENSSL_CONF=/dev/null also enables PQ but drops the crypto policy and changed the cipher list, so don't use it.

  • Python 3.9 to 3.11 on Lambda (AL2, OpenSSL 1.1.1): a sitecustomize.py shim patches urllib3 and botocore to use pyOpenSSL, whose bundled OpenSSL offers PQ. Set PYTHONPATH to the shim's directory. It covers requests and boto3, not ssl, http.client, aiohttp or httpx. It overrides a deliberate botocore choice and was tested with certificate verification off, so treat it as a bridge until the runtime upgrade.

Node.js (bundled OpenSSL)

Node compiles in its own OpenSSL; 22.20+ and 24.9+ ship 3.5. On Lambda the bootstrap sets OPENSSL_CONF=/var/runtime/openssl_conf/openssl.cnf, whose only setting is a group list without ML-KEM. The override is the same file with the PQ group added:

nodejs_conf = openssl_init
[openssl_init]
ssl_conf = ssl_sect
[ssl_sect]
system_default = system_default_sect
[system_default_sect]
Groups = *X25519MLKEM768:*X25519:secp256r1:X448:secp521r1:secp384r1:ffdhe2048:ffdhe3072:ffdhe4096:ffdhe6144:ffdhe8192

  • Set: OPENSSL_CONF=/var/task/pq-tls/openssl-pq-node.cnf.

  • Watch for drift: this file replaces AWS's rather than including it. Add a pipeline check that diffs AWS's file against ours, minus the PQ group.

  • Node 18 and 20: bundled OpenSSL is older than 3.5. No setting helps; upgrade.

Java (JSSE, independent of the OS)

Java's TLS stack doesn't use OpenSSL, so moving to AL2023 changes nothing for Java. JDKs before 25 have no ML-KEM groups.

  • Java 8 to 21: a Java agent (pq-tls-agent.jar, compiled for Java 8) registers Bouncy Castle 1.87 as the first JSSE provider and sets jdk.tls.namedGroups=X25519MLKEM768,x25519,secp256r1,secp384r1 unless already set. Set JAVA_TOOL_OPTIONS=-javaagent:/var/task/pq-tls/pq-tls-agent.jar.

  • Java 8 only: also add -Djdk.tls.client.protocols=TLSv1.3,TLSv1.2, since its client defaults to TLS 1.2.

  • Why an agent: the Lambda Java bootstrap's system classpath is /var/runtime/lib only, so providers registered through java.security from other paths are silently ignored.

  • Risk: Bouncy Castle becomes the TLS provider for the whole process. Test functions that use custom keystores, FIPS mode or mutual TLS first.

  • Java 25: Corretto 25.0.5 negotiates PQ with the stock SunJSSE provider.

Go (own TLS stack)

  • Needs both: a Go 1.24+ toolchain and a go directive of 1.24+ in go.mod. A 1.25 build of a module whose go.mod says 1.23 stayed classical in testing.

  • No-code override: GODEBUG=tlsmlkem=1 turned that build PQ, and can be set in the deployment config.

  • Pitfall: code that sets tls.Config.CurvePreferences gets no PQ.

Rust

rustls with the aws-lc-rs provider supports X25519MLKEM768. Sources disagree on which 0.23.x release made it the default (0.23.22 or 0.23.27). The AWS SDK for Rust defaults to PQ for crates published after 2025-08-29. Rebuild with current crates; apps on the openssl crate follow the system OpenSSL instead.

Inbound: front doors and TLS 1.3 enforcement

Inbound connections become PQ when the front door's TLS policy offers ML-KEM and the caller supports it. Allow TLS 1.2 and 1.3 first, measure, then move each endpoint to TLS 1.3 only once its TLS 1.2 traffic reaches zero. TLS negotiation already picks 1.3 when both sides support it, and TLS 1.3's downgrade protection stops an attacker forcing 1.2.

Rollout through build, package and release

Every change, including configuration, ships as a release here. So the fix lives in the shared build template, and each workload picks it up on its next release with no per-service code edits.

Rollout loop (diagram in the online doc): 1 Classify, 2 Change request, 3 Release, 4 Verify, repeated per release cycle.

The release step is the only one that changes a workload; the others are automation around it.

  1. Classify. The posture inventory sorts each workload into a matrix row and records the gap.

  2. Change request. A bot opens a pull request in each repo that bumps the shared module or template. The template ships the right files under /var/task/pq-tls/ (config file, agent jar or shim) and sets the matching variable. It leaves a workload's own OPENSSL_CONF alone and flags it for review. Bundling into the package avoids Lambda's 5-layer limit.

  3. Release. The normal pipeline builds, packages and releases. A guardrail (cfn-guard, OPA/conftest or a CloudFormation Hook) warns, then later fails, on Lambda and task definitions missing the PQ settings, and on non-PQ ELB policies.

  4. Verify. Observed signals confirm the workload's connections moved to PQ; shipping isn't proof. CLM tracks each workload as a campaign item.

Dormant workloads with no release coming: rank them by observed classical traffic. One making no classical outbound TLS doesn't need forcing; the rest get a no-op rebuild and release. Runtimes past AWS's block-update date can't be changed at all, so schedule those first.

Steps (every component)

  1. Toolchain. Set the build image or CI toolchain to Go 1.24 or later (current: 1.25). Go 1.23 and earlier have no X25519MLKEM768.

  2. go.mod. Raise the go line to 1.24 or later: go mod edit -go=1.24. Go picks some defaults from this line. A Go 1.25 binary of a module whose go.mod said 1.23 stayed classical in testing.

  3. If you can't raise go.mod yet, turn PQ on by itself. Either:

    • add //go:debug tlsmlkem=1 above package main, or a godebug tlsmlkem=1 line in go.mod (Documented by Go; not tested here), or

    • set GODEBUG=tlsmlkem=1 in the deployment config, with no code change (Tested).

  4. Code check. Search for CurvePreferences. Any tls.Config that sets it gets only the listed groups, so add tls.X25519MLKEM768 first: CurvePreferences: []tls.CurveID{tls.X25519MLKEM768, tls.X25519, tls.CurveP256}.

  5. Release through the normal pipeline.

Raising the go line also changes other defaults (for example certificate and HTTP behaviour listed in the Go release notes), so run the service's tests. The GODEBUG route changes only the TLS group.

Notes per component

  • Lambda: the go1.x managed runtime is retired; Go functions run on provided.al2023 or provided.al2 with a bootstrap binary. Both work, since the OS isn't involved.

  • Containers: no base-image change is needed. Builds using GOEXPERIMENT=boringcrypto or the Go FIPS 140-3 module weren't tested; check them separately.

  • AWS SDK for Go v2 uses crypto/tls, so it follows the rules above (Documented).

Verify

  • Posture, without running it: go version -m <binary>. The first line gives the Go version. A build DefaultGODEBUG= line containing tlsmlkem=0 means the binary is classical: go.mod is too old (Tested).

  • Live: point the service at a server that accepts only X25519MLKEM768; the handshake must succeed.

  • Observed: CloudTrail tlsDetails.keyExchange on its AWS calls shows X25519MLKEM768.

Lambda (zip), python3.9 to 3.11

These runtimes run on Amazon Linux 2 with OpenSSL 1.1.1zb, which has no ML-KEM. No config file helps.

  • Preferred: upgrade the runtime to python3.12 or later, then follow the section above. python3.9 is already deprecated, and after AWS's block-update date no change can be released.

  • Bridge, if the upgrade must wait:

    1. Add pq-tls/pyshim/sitecustomize.py to the package.

    2. Add pyopenssl and cryptography to the package (pip install --target <package> pyopenssl cryptography, built for the function's architecture). If the function already ships cryptography, keep its version unless it's too old for current pyOpenSSL.

    3. Set PYTHONPATH=/var/task/pq-tls/pyshim.

    4. Release, then confirm the log lines pq-tls: python legacy shim: urllib3 -> pyOpenSSL and botocore -> pyOpenSSL appear.

  • What the bridge covers: requests, urllib3 and boto3 became PQ on 3.9 and 3.11 in testing. Code using ssl, http.client, aiohttp or httpx directly stays classical.

  • Risks: it overrides botocore's deliberate use of the standard-library TLS context, and certificate verification against real endpoints hasn't been tested yet.

Backend leg

With a PQ listener policy, the load balancer's connection to TLS targets uses ELBSecurityPolicy-TLS13-1-0-PQ-2025-09. So a classical client still gets PQ on the load-balancer-to-target hop when the target supports ML-KEM. Which group is actually negotiated to the target isn't documented (third-party report).

Detect

  • ALB connection logs record the key exchange per connection; NLB access logs carry tls_keyexchange (Documented). Turn both on for every TLS listener and send them to the central log account.

  • Posture: AWS Config rule elbv2-predefined-security-policy-ssl-check with the PQ policy names as its allowlist flags non-PQ listeners. AWS also published a PQ-readiness conformance pack (blog, 2026-05-14) with custom rules for ELB and API Gateway.

  • Classic LBs: list them (aws elb describe-load-balancers); every one is a migration item.

Remediate

  1. In IaC, set SslPolicy (CloudFormation), sslPolicy (CDK) or ssl_policy (Terraform aws_lb_listener) to ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09. For EKS, set the AWS Load Balancer Controller annotation alb.ingress.kubernetes.io/ssl-policy.

  2. Release through the normal pipeline.

  3. Watch the logs: PQ share rises as clients upgrade; TLS 1.2 connections show which callers still need work.

  4. When a listener's TLS 1.2 count is zero for an agreed period, move it to the TLS 1.3-only PQ policy.

  5. Put remaining TLS 1.2 callers on a separate listener or hostname, tracked as exceptions.

AWS notes that PQ and non-PQ policies aren't compatible on listeners of the same load balancer, so move all of a load balancer's listeners together.

Enforce

  • SCP: deny elasticloadbalancing:CreateListener, ModifyListener and CreateLoadBalancer unless the elasticloadbalancing:SecurityPolicy condition key is one of the PQ policy names. This also stops drift from the Load Balancer Controller.

  • Pipeline: cfn-guard, OPA/conftest or Checkov custom rules on listener policy fields. No built-in Checkov, tfsec or Trivy PQ rule was found.

  • Config: the managed rule above, with SSM Automation calling elbv2 modify-listener for remediation if you allow out-of-pipeline fixes.

  • VPC Flow Logs carry no TLS data.

Remediate (convert what can't be upgraded)

  1. Upgrade clients first (language runbooks); conversion is for what's left: vendor appliances, closed-source software, legacy partners.

  2. Route that traffic through an egress tier that re-originates PQ: a PAN-OS or BIG-IP appliance, an SWG, or an Envoy egress gateway with ecdh_curves: [X25519MLKEM768, X25519].

  3. The client-to-converter hop stays classical, so keep it short and inside the VPC.

  4. Decrypting proxies break certificate pinning and mutual TLS; exclude those flows and record them as exceptions.

  5. Before enabling PQ through any inline device, test that it passes the roughly 1.2 KB larger ClientHello; some middleboxes drop it.

VPN

For site-to-site links that must be PQ today, a third-party VPN appliance with PQ IKEv2 (for example PAN-OS 11.2 or 12.1+) is the documented option. AWS-managed VPN has no published PQ path.

  1. Fleet inventory by TLS stack: for each device model, record firmware version, TLS library and version, and whether it can be updated over the air. IoT Device Management fleet indexing can hold these as thing attributes.

Remediate

  1. New devices: require a PQ-capable TLS stack in procurement and design: wolfSSL 5.8+ on microcontrollers, OpenSSL 3.5 on Linux-class devices. Budget for a ClientHello about 1.2 KB larger and the ML-KEM memory and CPU cost.

  2. Updatable devices: plan an over-the-air update to a PQ-capable stack, so they're ready when IoT Core adds a PQ policy.

  3. Devices that can't be updated: put a PQ-capable gateway in front (a Greengrass or edge box with OpenSSL 3.5 or wolfSSL, or a PQ tunnel such as an IPsec or SASE tunnel) for the long-haul hop. The last hop into IoT Core stays classical until AWS adds a PQ policy.

  4. Track AWS: watch for a PQ security policy in IoT Core; when it ships, move device endpoints to it per fleet, with the same allow-both-then-enforce approach as load balancers.

Risks

  • Larger ClientHellos and ML-KEM computation can exceed buffer sizes or battery budgets on constrained devices; test on real hardware.

  • Device lifetimes of 10 years or more mean devices bought now will be in service when quantum attacks matter; procurement is the cheapest point to fix this.

Certificates and signatures (ML-DSA)

ML-DSA (FIPS 204) replaces the signatures in certificates; it is the second step after ML-KEM key exchange. It is less urgent: recorded traffic can be decrypted later, but a signature only has to hold at the moment of the handshake. Today ML-DSA works in private PKI only, which is where the CLM product does the work.

Size cost: an ML-DSA-44 signature is 2,420 bytes and its public key 1,312 bytes, against 64 bytes for an ECDSA P-256 signature. Each chain grows by several kilobytes, which some middleboxes and IoT devices handle badly.

The CLM product's role

The CLM codebase already has ML-DSA plumbing: certificate policy (clm/internal/certpolicy/quantumsafe.go), HSM signing (clm/internal/hsm/craton_mldsa.go), the Nitro enclave signer (nitro-enclave/internal/pqc/signer.go), and composite and hybrid certificate tests. These were found by file name; the code paths weren't reviewed.

Split of responsibilities:

  • ML-KEM: discovery plus runtime and config fixes (the rest of this document).

  • ML-DSA: a CLM re-issuance campaign. Start with internal mutual TLS, service-to-service and code signing; public endpoints wait for the web PKI.

Steps

  1. Finish ML-KEM rollout first; it protects against the urgent threat.

  2. Inventory certificate signature algorithms in CLM, starting with long-lived roots and intermediates.

  3. Pilot ML-DSA, or composite ML-DSA with ECDSA, on one internal mutual TLS path through CLM or Private CA. Confirm every client on the path can verify the chain: OpenSSL 3.5 and Bouncy Castle support ML-DSA; the stock JDK added the ML-DSA signature API in JDK 24, but whether its TLS stack accepts ML-DSA certificates is unconfirmed.

  4. Expand per path, keeping classical fallbacks where verifiers lag.

  5. Public certificates when CA/Browser Forum rules and browsers allow.
