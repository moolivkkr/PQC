Corrections from the end-to-end run and the document review

We ran every remediation in the guide against a TLS observer on an isolated LocalStack, across EC2, ECS Fargate, ECS on EC2 and Lambda, for all five languages. Six instructions did not behave as written. All six are now fixed in the guide sources, the kit and the generated configs, and each is kept as a regression case.

What changed in the guide

Java 8

JDK 8 with the BouncyCastle kit fails every handshake through HttpsURLConnection

Guide saidJDK 8 plus the kit plus -Djdk.tls.client.protocols gives PQ.
ObservedBCJSSE endpoint identification raises "No hostname specified for HTTPS endpoint ID check" (bc-java#1656). The TLS 1.2-only default comes from the Lambda Java 8 runtime, not from JDK 8 itself.

FixAdd -Dorg.bouncycastle.jsse.client.assumeOriginalHostName=true. The layer wrapper now adds it automatically. Updated in 06-java.md, 01-overview.md, template.yaml and the wrapper.

.NET

Guard rule PQ-L2 accepted a wrapper that did nothing for .NET

Guide saidThe pq-tls layer wrapper covers dotnet8 and dotnet10, and PQ-L2 accepts it.
ObservedThe wrapper had no dotnet branch. Functions passed the guard and still negotiated classical key exchange.

FixThe wrapper now has a dotnet branch that sets OPENSSL_CONF when it is unset. PQ-L2 is now accurate without a rule change.

.NET

Client certificate import fails on Lambda before any handshake

Guide saidRe-import into the CurrentUser/My store at start-up.
ObservedOn Lambda the user's home directory is read-only, so X509Store cannot write.

FixSet HOME=/tmp on Lambda. Updated in 07-dotnet.md.

Python

The legacy bridge for Python 3.9 to 3.11 breaks every HTTP request

Guide saidpip install pyopenssl cryptography.
ObservedLambda Python 3.9 to 3.11 lack idna, so every urllib3, requests and boto3 call raises ModuleNotFoundError. The 3.11 abi3 wheel also fails on 3.9 and 3.10.

FixAdd idna and build the layer inside each version's Lambda image (pinned: cryptography==50.0.2 pyOpenSSL==26.4.0 idna==3.20). Updated in 04-python.md, 02-runbook.md, 22-config-index.md.

Node.js

"Node 20 is never PQ" is wrong on AL2023

Guide saidNo setting adds PQ to Node 20.
ObservedAL2023 dnf install nodejs20 links the system OpenSSL 3.5.8 and negotiates PQ with OPENSSL_CONF or the DEFAULT:PQ policy. Lambda nodejs18.x/20.x bundle OpenSSL 3.1.8 and 3.2.6 (not 3.0.x) and have no ML-KEM.

FixDecide by process.versions.openssl, not the Node major version. On Lambda Node 18/20, use the pq-egress extension as the interim. Updated in 05-nodejs.md, 01-overview.md.

Go

FIPS mode offers more curves than the guide listed

Guide saidFIPS modes offer "P-256 only" or "hybrids + P-256".
ObservedThe client also offers P-384 and P-521.

FixTables in 03-go.md and the go-pq-lint.sh message now say "P-256, P-384, P-521" and "NIST curves only, no PQ".

Document review, 2026-11-16

Every document and the deck were checked against the test results. Every e2e case the documents cite exists in the results. The deck's case counts match the results by language and compute type. These were wrong or out of date and are fixed (commits 42890f7, c6e5cd3):

Guardrail

PQ-L2 rejected the guide's own Lambda fix

The guide bundles the config at /var/task/pq-tls/; the Guard, Config, Rego and Checkov rules accepted only /opt/pq-tls/. All four accept both now. Retested with cfn-guard 3.2.1 and OPA (12/12). Found by the RemediationEngine team's read of the guide.

Guardrail

Dockerfile rule warned on PQ Python images and missed old Node pins

python:3.9 to 3.11 default to Debian trixie with OpenSSL 3.5, so they are PQ; only -bookworm and -bullseye tags are classical. Node tags pinned below 22.20 or 24.5 now warn. Tested with conftest on 12 base images.

Envoy

"Envoy has no ML-KEM by default" is true only before 1.40

Envoy 1.40.2 with no ecdh_curves negotiated X25519MLKEM768 with a PQ-only client and reached a PQ-only backend (tested). The Web servers, Service mesh and Network tabs now give the version.

Java

Lambda now has java8/11/17 on AL2023 as well as AL2

AWS lists java8.al2023, java11.al2023 and java17.al2023. Guardrail PQ-L3 and the layer's compatible runtimes now include them. The e2e suite tested the AL2 variants and the java:8.al2023 image; the newer 11 and 17 runtimes are marked untested.

Lambda

Deprecation dates were "not confirmed"

AWS's runtime page lists them: nodejs18/20, python3.9/3.10, provided.al2 and dotnet8 are already deprecated; python3.11 and the AL2 Java runtimes follow on 2027-06-30. Updates are blocked from 2027-08-31 for all of them.

Labels

Evidence labels written before the e2e run

Go on Fargate, ECS and EC2, JDK 11 with kit v2, the Java layer on Lambda, the .NET DEFAULT:PQ server and Tomcat's OpenSSL connector said "not run" or "Unverified" although tests now cover them. They cite the cases now. The overview's Tested label and evidence section include the LocalStack suite.

What this run does not prove

  • The ALB/NLB listener leg (client to load balancer). LocalStack's ALB ignores the security policy: a ELBSecurityPolicy-2016-08 listener still negotiated X25519MLKEM768 with LocalStack's own certificate. API Gateway and CloudFront are not tested either. These need real AWS.
  • The load balancer to container leg is tested, as a model: 32 cases (srv-*) where the observer connects to each language's HTTPS container the way the ALB's PQ backend policy does. Unfixed containers stay classical, fixed ones negotiate X25519MLKEM768, and the certificate never changes. It models AWS's ClientHello with Go's TLS client, not AWS's s2n-tls.
  • KMS, SSM and Secrets Manager endpoints, and the AWS Parameters and Secrets Lambda Extension. pq-egress stands in for that pattern and has not been tested with SigV4 SDK calls.
  • The AMI disk image and kernel. EC2 cases use containers built from the AMI's release packages, so the TLS userland matches but the kernel is Docker Desktop's.
  • Lambda on Firecracker. Functions run in AWS's runtime images under LocalStack's emulation.
  • x86_64. Everything ran on arm64.

Two LocalStack artefacts are documented so they are not mistaken for guide errors: it drops HOME from Lambda environment variables (AWS does not), and its EC2 service times out under parallel runs.
