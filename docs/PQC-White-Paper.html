1 Introduction

1.1 What we are solving

Every TLS connection we own agrees its session key with a classical key exchange (X25519 or ECDHE P-256) unless something changes it. Traffic recorded today can be decrypted once a large quantum computer exists ("harvest now, decrypt later"), so data that must stay confidential for years is exposed now.

  • Classical is still the default where we run. On Lambda and Amazon Linux 2023, Python, Node.js and .NET negotiate classical X25519; Java before 25 and Node.js 18 and 20 cannot negotiate PQ at all.
  • It fails silently. A PQ client and a classical server, or the reverse, quietly agree on classical. Only logs, sensors and the inventory show it.
  • One date is fixed. AWS blocks updates to deprecated Lambda runtimes (Node.js 18 and 20, Python 3.9 to 3.11, Java on Amazon Linux 2, provided.al2, dotnet8) from 2027-08-31. After that no fix can be added to them.

1.2 What "PQC-enabled" means

Term Meaning Proven by
PQ connection TLS 1.3 handshake that negotiated a hybrid ML-KEM group (X25519MLKEM768; ML-KEM is FIPS 203) The negotiated group in CloudTrail, ELB logs, Zeek or the application log
PQ-enabled client or server Offers or accepts the hybrid group first and still accepts classical peers A PQ-only and a classical-only test server both connect
PQ-done workload Every connection it owns that can be PQ is observed as PQ; the rest are recorded exceptions Dashboards, not the deployment record
PQ-signed certificate Certificate or signature using ML-DSA (FIPS 204). A separate, slower track Certificate algorithm; TLS signature algorithm

It does not mean new certificates (ML-KEM works with today's RSA and ECDSA certificates), PQ-only endpoints (classical fallback stays until logs show no classical traffic), encryption at rest, or FIPS-validated PQ.

1.3 Scope

Connections: internet to front doors (ALB, NLB, CloudFront, API Gateway); front door to target; workload to AWS APIs, internal services, third parties and data stores; SSH to hosts; devices to AWS IoT Core; and certificates and signatures. Compute: Lambda (zip and image), ECS on Fargate, ECS on EC2 and EKS, EC2. Languages: Go, Python, Node.js, Java, .NET.

2 Use cases: key exchange and certificates

ML-KEM protects key exchange and stops traffic recorded today from being read later: urgent for every connection, and no new certificates. ML-DSA protects certificates and signatures: a forged signature matters only once a quantum computer exists, so it is urgent only where trust must last for years. In TLS today, "hybrid" key exchange is one group (X25519MLKEM768); "hybrid" certificates mean a dual certificate (the server holds ECDSA and ML-DSA and sends what the client asks for). Composite certificates have no TLS code points yet (Documented).

Use case Key exchange (ML-KEM) Certificate (ML-DSA) Do now
Public HTTPS PQ policy on ALB, NLB, CloudFront, API Gateway REST Not possible: AWS front doors and browsers serve RSA/ECDSA only Key exchange now; keep ECDSA certificates
Internal HTTPS (private CA) Language fix per workload Dual certificate from AWS Private CA; OpenSSL 3.5 clients get ML-DSA, Go and Java get ECDSA Key exchange now; pilot dual certificates. Never ML-DSA-only
Workload identity and mTLS Same as internal ML-DSA client keys work on OpenSSL 3.5 stacks and .NET 10; not .NET 8, Go, Java. IAM Roles Anywhere accepts ML-DSA Pilot Roles Anywhere; mesh identities stay ECDSA
User certificates Windows Schannel opt-in AD CS 2025 issues ML-DSA; Microsoft calls Schannel ML-DSA a pilot Separate test CA only
Devices and IoT AWS IoT Core has no PQ policy IoT Core: RSA/ECDSA only Plan now: ML-DSA root alongside ECDSA in new firmware
Code and firmware signing n/a KMS ML-DSA keys; Private CA code-signing certificates; AWS Signer is ECDSA only Plan now: add an ML-DSA signature for artifacts verified for years
SSH OpenSSH 10 defaults to mlkem768x25519-sha256 (Tested) OpenSSH 10.6 hybrid ML-DSA keys Upgrade OpenSSH; ML-DSA keys only where all clients are 10.6+

Tested across 409 client cases: 91 used ML-DSA on all three test targets, 4 (.NET 8) on server certificates only, 307 got ECDSA from the dual server, and every client that connects at all still connected to the dual server. So ML-DSA roots can be distributed now, and dual certificates break nobody; ML-DSA-only servers would break Go, Java, OpenSSL 3.0 and the default Amazon Linux 2023 policy.

3 Detection

Two kinds of signal, used together. Observed signals show what a handshake negotiated and prove a fix worked. Posture predicts what a workload will negotiate from its runtime, versions and settings, and covers what no log or sensor sees (Lambda and Fargate calls to non-AWS services). A TLS 1.2 connection is never PQ, so the protocol version alone flags it.

Signal Sees Covers Evidence

ALB connection logs, NLB TLS access logs Group per inbound connection Every ALB and NLB TLS listener (logs off by default) Documented
Zeek on VPC Traffic Mirroring ssl.log curve; our script adds pq and raises a notice East-west and egress traffic of EC2 hosts, ECS and EKS nodes, NAT instances, proxies Tested: Zeek 7.2.2 classified every handshake in the e2e stack; 8.0.10 on a pcap
Application handshake log One JSON line per handshake Any compute, including Lambda and Fargate Tested: a CloudWatch filter found 892 of 892 classical handshakes

Posture inventory Runtime, settings, policies, classified Everything AWS APIs list Tested on LocalStack: 25 of 25
Compute AWS API calls Other outbound Packet capture
Lambda CloudTrail Posture or application log only No
Fargate CloudTrail Posture, application log or an egress proxy No
ECS on EC2, EKS, EC2 CloudTrail Zeek on mirrored ENIs Yes (Nitro)

Zeek is the only signal for east-west and egress traffic that no AWS log covers, whatever made the connection. Mirror only TLS ports from NAT instances, egress proxies and busy hosts; don't truncate packets (the hybrid ClientHello spans two segments); write JSON logs to S3 for Athena. It cannot see Fargate or Lambda, nor certificate types in TLS 1.3.

Blind spots and their cover: Lambda and Fargate to non-AWS services (posture, app logs, egress proxy); AWS APIs not yet logging keyExchange (posture); AWS-managed legs such as CloudFront to origin and API Gateway to integrations (recorded exceptions); IoT Core (device inventory).

4 Inventory and dashboards

The inventory is one list of everything that makes or ends a TLS connection, each with a status, an owner and a next action. A component is done when its posture is PQ and observed signals show no classical connections for seven days, or when it is a recorded exception.

Status Meaning Next action
pq PQ today with no change Confirm with observed signals
pq-fixed Our fix is applied Confirm; classical traffic here means a failed fix
bridge Partial fix (Python 3.9 to 3.11 shim, pq-egress extension) Plan the runtime upgrade
fixable One change makes it PQ Release the fix
upgrade Only a runtime upgrade helps Schedule before the block-update date
blocked AWS offers no PQ option Migrate, front it, or record an exception
scan Needs an image or binary scan Scan

Sources. Lambda functions, ECS task definitions, ELB listeners, Classic load balancers and API Gateway are read by configs/inventory/pq_inventory.py (read-only; Tested on LocalStack, 25 of 25 components classified correctly). Next to add: container image scans (Inspector SBOM), EC2 hosts (SSM Inventory), EKS workloads, RDS and data services, certificates (ACM, Private CA), CloudFront and IoT devices.

Pipeline. Inventory output, CloudTrail, ELB logs, Zeek ssl.log and application handshake logs land in S3; Athena views (configs/inventory/athena-views.sql) put them in one shape and join observed calls to workloads by IAM role; dashboards in QuickSight or Managed Grafana read the views. The views follow documented log formats but have not been run on Athena (Unverified).

Lambda ships the fix three ways, in order of preference: bundled in the package by the build template (no layer limit); the pq-tls layer with AWS_LAMBDA_EXEC_WRAPPER (one layer for all runtimes, PQ_TLS_DISABLE=1 rolls back); or, interim, the pq-egress extension, which makes the TLS connection for runtimes that cannot (the app calls it over loopback). 6.1 Go

What decides PQ. Go's own crypto/tls is compiled into the binary, so the OS, base image and Lambda runtime play no part. Three things decide the result: the toolchain version, the go line in go.mod, and any explicit TLS settings in code. A binary built with Go 1.24+ and a go line of 1.24+ negotiates X25519MLKEM768 by default on every compute type.

Compute PQ today? What to change
Lambda (provided.al2023, provided.al2) Yes with Go 1.24+ and go ≥ 1.24 Rebuild with Go 1.26, raise the go line; or GODEBUG=tlsmlkem=1
ECS Fargate, ECS on EC2, EKS Same rule; the base image does not matter Same
EC2 Same rule Same; the systemd unit can carry GODEBUG

What to change, in order

  1. go version -m <binary> shows Go 1.23 or older: rebuild with Go 1.26. Nothing else helps (1.23 offers only the pre-standard Kyber draft).
  2. The go line is below 1.24: raise it to 1.26. If you can't yet, godebug tlsmlkem=1 in go.mod or GODEBUG=tlsmlkem=1 in the deployment.
  3. Code or a library sets CurvePreferences or MaxVersion: tls.VersionTLS12: add X25519MLKEM768 or remove the setting.
  4. FIPS mode: use Go 1.26+ native FIPS 140-3 (1.24 has no PQ in FIPS mode; fips140=only on 1.25 fails every handshake). The AWS SDK for Go v2 in FIPS mode forces classical curves: re-add the hybrids with WithTransportOptions.

Certificates and keystores: no change. Watch two things: SSL_CERT_FILE replaces the system bundle rather than adding to it, and x/crypto/pkcs12 cannot read OpenSSL 3 PKCS#12 files (use go-pkcs12). ML-DSA: Go 1.23 to 1.27 never negotiate ML-DSA in TLS; they get the ECDSA certificate from a dual-certificate server and fail an ML-DSA-only one.

Rollback: GODEBUG=tlsmlkem=0,tlssecpmlkem=0 in the environment; no rebuild. Detect: CloudTrail for AWS calls; Go 1.25+ can log ConnectionState().CurveID itself.

Tested: 118 client cases (Lambda 77, Fargate 22, ECS on EC2 5, EC2 14) and 5 load balancer target cases, all passing, covering Go 1.23 to 1.27, every go line, GODEBUG, FIPS modes and the AWS SDK fix.

6.2 Python

What decides PQ. The standard library ssl module uses the platform's OpenSSL, so the OS image and its crypto policy decide. OpenSSL 3.5 can do ML-KEM, but Amazon Linux 2023's crypto policy leaves it out, so Lambda and AL2023 images negotiate classical X25519 until a config file adds it. Libraries that bundle their own TLS (grpcio, awscrt, psycopg binary, pyOpenSSL, confluent-kafka) are already PQ on every runtime.

Compute PQ today? What to change
Lambda python3.12 to 3.14 No Ship openssl-pq.cnf, set OPENSSL_CONF=/var/task/pq-tls/openssl-pq.cnf (or the pq-tls layer)
Lambda python3.9 to 3.11 (Amazon Linux 2, OpenSSL 1.1.1) No Upgrade to 3.12+ before 2027-08-31. Bridge: the shim (requests and boto3 only) or the layer
Fargate, ECS on EC2, EKS Debian 13 (-trixie) and Alpine 3.24: yes. Debian 12, Ubuntu 24.04, AL2023: no Move to a trixie or Alpine image; on AL2023, DEFAULT:PQ in the Dockerfile or the config file
EC2 AL2023: no; Debian 13, Ubuntu 26.04: yes update-crypto-policies --set DEFAULT:PQ via SSM, or OPENSSL_CONF in the service unit

What to change, in order

  1. Pick the row above; one file and one variable, or one base image change.
  2. Don't use OPENSSL_CONF=/dev/null: it enables PQ but drops the crypto policy and changes the cipher list.
  3. Remove set_ecdh_curve(...) and TLS 1.2 maximums from code; on Python 3.15, SSLContext.set_groups() is the right API if you must pin groups.
  4. Python 3.9 to 3.11 bridge: build pyOpenSSL, cryptography and idna in each version's Lambda image (without idna every request fails); truststore.inject_into_ssl() disables it.

Certificates and keystores: no change for load_cert_chain, cafile, certifi or REQUESTS_CA_BUNDLE. gunicorn with an encrypted key file fails every worker: use an ssl_context hook. ML-DSA: works on OpenSSL 3.5 images (Debian 13, Alpine) and through the 3.9 to 3.11 shim; AL2023 also needs SignatureAlgorithms (openssl-pq-mldsa.cnf or DEFAULT:PQ).

Rollback: remove OPENSSL_CONF (or PQ_TLS_DISABLE=1 with the layer). Detect: CloudTrail for AWS calls; log SSLSocket.group() on Python 3.15+.

Tested: 59 client cases (Lambda 35, Fargate 13, ECS on EC2 3, EC2 8) and 6 load balancer target cases, all passing.

6.3 Node.js

What decides PQ. Official Node.js binaries bundle their own OpenSSL: 22.20+ and 24.5+ ship OpenSSL 3.5 and are PQ by default (use 24.9+ as the policy floor, as AWS does). On Lambda, the runtime's bootstrap sets OPENSSL_CONF to a file whose group list has no ML-KEM, so Lambda Node is classical until that file is overridden. Official Node 18 and 20 bundle OpenSSL without ML-KEM (3.0 in node:20 images; 3.1 and 3.2 on Lambda nodejs18.x and nodejs20.x). Distro Node links the system OpenSSL, so AL2023 dnf Node, even nodejs20, is fixable with the system policy or config.

Compute PQ today? What to change
Lambda nodejs22.x, nodejs24.x No (bootstrap config) Ship openssl-pq-node.cnf, set OPENSSL_CONF to it (or the pq-tls layer). Prefer 24: nodejs22.x updates are blocked from 2027-08-31
Lambda nodejs26.x (preview) Not sure: the base image is PQ unless AWS_LAMBDA_TLS_PROFILE=aws selects its classical profile (Docker test only) Set OPENSSL_CONF as for 22 and 24
Lambda nodejs18.x, nodejs20.x No, and no setting helps Upgrade before 2027-08-31; interim, the pq-egress extension for calls that must be PQ
Fargate, ECS on EC2, EKS Official node images 22.20+ and 24.5+: yes. AL2023 dnf Node: no Official image 24.9+; AL2023 dnf Node: DEFAULT:PQ in the Dockerfile or OPENSSL_CONF (EKS not tested)
EC2 Official binaries: yes. AL2023 dnf Node: no Official binaries, or DEFAULT:PQ / a per-service OPENSSL_CONF for dnf Node

What to change, in order

  1. Lambda: ship the override file and variable. Our file replaces AWS's rather than including it, so add a pipeline check that diffs AWS's file against ours on each new runtime image.
  2. Upgrade Node 18 and 20; don't put X25519MLKEM768 first in ecdhCurve on bundled Node 20: it crashes.
  3. Remove explicit ecdhCurve lists and TLS 1.2 maximums, or add X25519MLKEM768 to them.

Certificates and keystores: no change for key/cert, modern PFX, ca or NODE_EXTRA_CA_CERTS. Legacy RC2 or 3DES PFX files fail on every current runtime: re-export them. The Lambda image has an empty system CA store: set SSL_CERT_FILE. ML-DSA: Node on OpenSSL 3.5 (Lambda 22 and 24 even unfixed, official 22.20+/24.5+ images, fixed AL2023 Node) negotiates ML-DSA on all three targets; unfixed AL2023 Node and Node 20 get ECDSA.

Rollback: remove OPENSSL_CONF (or PQ_TLS_DISABLE=1 with the layer). Detect: CloudTrail for AWS calls; application handshake logs.

Tested: 93 client cases (Lambda 48, Fargate 28, ECS on EC2 5, EC2 12) and 7 load balancer target cases, all passing (LocalStack, run r1117041043; not yet on real AWS).

6.4 Java

What decides PQ. The JSSE provider inside the JVM, not OpenSSL, so the OS and image do not matter. JDK 25.0.5+ negotiates X25519MLKEM768 by default (JEP 527, backported to 25.0.5). JDK 8 to 21 have no ML-KEM; the fix is Bouncy Castle JSSE as the TLS provider, loaded by our kit v2 agent, or a move to JDK 25.

Compute PQ today? What to change
Lambda java8.al2, java11, java17, java21 No Kit v2 agent: JAVA_TOOL_OPTIONS=-javaagent:/var/task/pq-tls/pq-tls-agent.jar (or the pq-tls layer, which adds the Java 8 flags)
Lambda java25 Yes Nothing
Fargate, ECS on EC2, EKS JDK 25.0.5+ images: yes; 8 to 21: no Move to Corretto or Temurin 25.0.5+, or the agent, or a static java.security Bouncy Castle entry (17, 21)
EC2 Same as containers Same; JAVA_TOOL_OPTIONS in the service unit

What to change, in order

  1. Prefer JDK 25.0.5+ where the application can move. Oracle plans backports to 21 and 17, then 11 and 8; secondary reports say H1 and H2 2027 (Claimed, not shipped).
  2. Otherwise, the kit v2 agent. Java 8 also needs -Djdk.tls.client.protocols=TLSv1.3,TLSv1.2 on Lambda and -Dorg.bouncycastle.jsse.client.assumeOriginalHostName=true everywhere.
  3. Servers with an EC certificate need ssl.KeyManagerFactory.algorithm=PKIX under Bouncy Castle, or every handshake fails. Kit v2 sets it; code that hard-codes SunX509 (or Tomcat keyManagerAlgorithm="SunX509") still fails, and the CI check flags it.
  4. Without Bouncy Castle: Netty tcnative-boringssl 2.0.85, or the AWS SDK v2 CRT client (PQ by default from 2.35.11 per AWS; 2.59.1 Tested PQ, 2.35.10 classical).

Certificates and keystores: no change to JKS or PKCS#12 stores, cacerts or javax.net.ssl.trustStore; mutual TLS works with kit v2 (kit v1 silently sent no EC client certificate). Risk: Bouncy Castle becomes the TLS provider for the whole process: test FIPS, custom keystore and mutual TLS services first. ML-DSA: no JDK negotiates ML-DSA in TLS yet; Java gets ECDSA from a dual-certificate server.

Rollback: remove the -javaagent option. Detect: CloudTrail for AWS calls; server logs for inbound.

Tested: 96 client cases (Lambda 57, Fargate 21, ECS on EC2 5, EC2 13) and 7 load balancer target cases, all passing; Tomcat 11, Jetty 12 and the JDK HttpsServer with EC certificates on JDK 17 and 21 under kit v2, and EC keystores on JDK 25 with no change (container tests). Not yet run: real AWS, JDK 8 on EC2, FIPS.

6.5 .NET

What decides PQ. .NET has no API for TLS groups: it uses the operating system's stack, OpenSSL on Linux and Schannel on Windows. So the base image and its crypto policy decide, exactly as for Python. Lambda's dotnet8 and dotnet10 runtimes have OpenSSL 3.5 under the AL2023 policy, which leaves ML-KEM out.

Compute PQ today? What to change
Lambda dotnet8, dotnet10 (zip, image, Native AOT) No Ship openssl-pq.cnf, set OPENSSL_CONF (or the pq-tls layer). dotnet8 is deprecated: creation blocked from 2027-07-29, updates from 2027-08-31; move to dotnet10
Fargate, ECS on EC2, EKS 8.0-alpine, 10.0-alpine, 10.0-resolute (Ubuntu 26.04): yes. Default 8.0 and 10.0 tags, -noble, Azure Linux, AL2023: no Use an Alpine or resolute image; on AL2023 the config file or DEFAULT:PQ
EC2 Linux AL2023: no DEFAULT:PQ via SSM, or OPENSSL_CONF in the service unit
Windows Opt-in, not tested Schannel group X25519_MLKEM768 (TLS 1.3 only) via GPO or SSM, after the July 2026 update

What to change, in order

  1. Pick the row above. There is nothing to change in code, and nothing code can do.
  2. Remove EnabledSslProtocols = Tls12 caps: ML-KEM needs TLS 1.3.
  3. On Lambda, code that opens an X509Store needs a writable HOME: export HOME=/tmp from an exec wrapper in the package (tested), or load the PFX/PEM directly.

Certificates and keystores: no change for PFX, PEM, X509Store, custom validation callbacks or CustomTrustStore. X509Certificate2.CreateFromPemFile(caPath) throws on a CA-only file: use CreateFromPem(File.ReadAllText(path)). ML-DSA: .NET 10 on Alpine, resolute or AL2023 with DEFAULT:PQ accepts ML-DSA server certificates and presents ML-DSA client certificates (client side tested; a .NET server with an ML-DSA certificate was not). The openssl-pq.cnf route (Lambda, AL2023 config) adds ML-KEM only: ML-DSA-only servers fail. .NET 8 receives ML-DSA server certificates but cannot load an ML-DSA client key.

Rollback: remove OPENSSL_CONF (or PQ_TLS_DISABLE=1 with the layer), revert the FROM line, or update-crypto-policies --set DEFAULT. Detect: CloudTrail for AWS calls; .NET does not expose the negotiated group, so application logs cannot prove PQ.

Tested: 71 client cases (Lambda 33, Fargate 25, ECS on EC2 6, EC2 7) and 7 load balancer target cases, all passing, on LocalStack and Docker (not real AWS). Not tested: EKS, Windows, FIPS hosts.

8 Enforcement and guardrails

Guardrails keep new work PQ while the backlog is fixed. All start in warn mode and move to fail on a schedule; each step is reversible by flipping the mode.

Layer Controls Evidence
Organisation SCP on ELB and API Gateway security policies; optional RCP for TLS 1.3 on named S3 buckets; Config rules for ELB, API Gateway and CloudFront policies and a Guard rule for Lambda settings Documented; JSON and rules Tested on samples
Pipeline cfn-guard (14 rules) and a CloudFormation Guard Hook; conftest on Terraform plans; Checkov; Dockerfile and SBOM policies; check-go-pq.sh, check-jdk-pq.sh Tested on good and bad samples
Kubernetes Kyverno (audit, then deny) and Gatekeeper for ALB Ingress, NLB Service, ingress-nginx, istiod and pod variables Tested (CLI)
Runtime CloudTrail metric filter and alarm; EventBridge rules on non-PQ changes; hourly classical share from ELB logs; Zeek notices Partly Tested; AWS-side Unverified

Schedule: week 0 inventory and warn everywhere; week 2 block new risk (SCP on new OUs, pipeline fails on changed resources); week 6 fail all resources in CI with exceptions for the rest; week 8 org-wide SCP. Exceptions carry an owner, a reason (blocked by AWS, third party, legacy client) and a review date. Security Hub ELB.17 passes non-PQ policies, so a green control does not mean PQ.

9 Rollout, gaps and open items

Mechanism. Every change ships as a release: (1) the inventory classifies each workload; (2) a bot opens a pull request bumping the shared build template, which adds the right file and variable; (3) the normal pipeline releases it, with guardrails warning then failing; (4) observed signals confirm the change, because shipping is not proof. Dormant workloads are ranked by observed classical traffic; runtimes past AWS's block date cannot change, so they go first.
