1 Summary for Node.js teams

What decides PQ. Official Node.js binaries bundle their own OpenSSL: 22.20+ and 24.5+ ship OpenSSL 3.5 and are PQ by default (use 24.9+ as the policy floor, as AWS does). On Lambda, the runtime's bootstrap sets OPENSSL_CONF to a file whose group list has no ML-KEM, so Lambda Node is classical until that file is overridden. Official Node 18 and 20 bundle OpenSSL without ML-KEM (3.0 in node:20 images; 3.1 and 3.2 on Lambda nodejs18.x and nodejs20.x). Distro Node links the system OpenSSL, so AL2023 dnf Node, even nodejs20, is fixable with the system policy or config.

Compute PQ today? What to change
Lambda nodejs22.x, nodejs24.x No (bootstrap config) Ship openssl-pq-node.cnf, set OPENSSL_CONF to it (or the pq-tls layer). Prefer 24: nodejs22.x updates are blocked from 2027-08-31
Lambda nodejs26.x (preview) Not sure: the base image is PQ unless AWS_LAMBDA_TLS_PROFILE=aws selects its classical profile (Docker test only) Set OPENSSL_CONF as for 22 and 24

What to change, in order

  1. Lambda: ship the override file and variable. Our file replaces AWS's rather than including it, so add a pipeline check that diffs AWS's file against ours on each new runtime image.
  2. Upgrade Node 18 and 20; don't put X25519MLKEM768 first in ecdhCurve on bundled Node 20: it crashes.
  3. Remove explicit ecdhCurve lists and TLS 1.2 maximums, or add X25519MLKEM768 to them.

Certificates and keystores: no change for key/cert, modern PFX, ca or NODE_EXTRA_CA_CERTS. Legacy RC2 or 3DES PFX files fail on every current runtime: re-export them. The Lambda image has an empty system CA store: set SSL_CERT_FILE. ML-DSA: Node on OpenSSL 3.5 (Lambda 22 and 24 even unfixed, official 22.20+/24.5+ images, fixed AL2023 Node) negotiates ML-DSA on all three targets; unfixed AL2023 Node and Node 20 get ECDSA.

Rollback: remove OPENSSL_CONF (or PQ_TLS_DISABLE=1 with the layer). Detect: CloudTrail for AWS calls; application handshake logs.

Tested: 93 client cases (Lambda 48, Fargate 28, ECS on EC2 5, EC2 12) and 7 load balancer target cases, all passing (LocalStack, run r1117041043; not yet on real AWS).

2 Context for application teams

2.1 What "PQC-enabled" means

A PQ connection is a TLS 1.3 handshake that negotiated a hybrid ML-KEM key exchange group, X25519MLKEM768 (ML-KEM is FIPS 203). It protects traffic recorded today from being decrypted by a future quantum computer. Your service is PQ-enabled when it offers or accepts that group first and still connects to classical peers, so nothing breaks. It is done when the programme's dashboards show its connections as PQ, not when the change is deployed.

What does not change: your certificates, keystores, private CA trust and mutual TLS. ML-KEM works with today's RSA and ECDSA certificates. ML-DSA (PQ certificates, FIPS 204) is a separate, later track; your summary page says what your runtime can do with it.

2.2 How the fix ships

Every fix is one of: a configuration file plus a variable, a Java agent, a base image or a version. The shared pq-tls kit versions these files once, and the shared build template adds them, so your service picks the fix up on its next release and rolls back by removing one setting. Guardrails in the pipeline warn first and fail later on settings that block PQ.

Where a variable goes How
Lambda (zip or image) Environment.Variables (CloudFormation, SAM), environment (CDK, Terraform)
Container images ENV NAME=value in the Dockerfile
ECS task, EKS pod (override) containerDefinitions[].environment; spec.containers[].env
EC2 service Environment=NAME=value in the systemd unit

3 Node.js: detailed guide

3.1 Problem statement

Official Node.js 22.20+ and 24.5+ negotiate hybrid post-quantum key exchange (X25519MLKEM768) with no change. Four groups stay classical (X25519 or P-256 alone), so traffic recorded today can be decrypted once a large quantum computer exists ("harvest now, decrypt later"):

Group Why it is classical Fix
Lambda nodejs22.x, nodejs24.x (zip and AWS base image) The bootstrap sets OPENSSL_CONF to a file whose Groups omits ML-KEM Ship openssl-pq-node.cnf and point OPENSSL_CONF at it
Official Node 20 and older, 22.0–22.19, 24.0–24.4; Lambda nodejs18.x, nodejs20.x Bundled OpenSSL has no ML-KEM (3.0.x; Lambda 18 = 3.1.8, Lambda 20 = 3.2.6) Upgrade; no setting helps
Distro Node on Amazon Linux 2023 (dnf install nodejs20/22/24) Links the system OpenSSL 3.5.8, whose DEFAULT crypto policy omits ML-KEM DEFAULT:PQ policy, or OPENSSL_CONF = openssl-pq-node-system.cnf
Code that pins groups or caps TLS at 1.2 ecdhCurve / tls.DEFAULT_ECDH_CURVE without X25519MLKEM768, maxVersion: 'TLSv1.2', --tls-max-v1.2 Remove the setting, or put X25519MLKEM768 first

What decides, in order: the OpenSSL inside the node process (bundled in official builds, the system library in distro builds), the OpenSSL config file Node reads, then TLS options in code. The OS crypto policy matters only for distro-built Node. Node reads the nodejs_conf section of the file named by --openssl-config or OPENSSL_CONF (the flag wins); --openssl-shared-config makes it read openssl_conf instead; both flags are allowed in NODE_OPTIONS (Node CLI docs, Documented).

Certificates, keys, PFX files, CA bundles and client certificates take no part in the key-exchange choice: every existing-certificate, custom-trust and mutual-TLS setup tested kept working unchanged (cases C, D, E). Every client library tested (fetch, undici, axios, got, node-fetch, AWS SDK v3, grpc-js, pg, mysql2, ioredis, kafkajs) inherits Node's defaults.

Beyond compute type (Quick start covers the runtime):

C. Existing server certificates, keys and PFX files

Who this is: your server loads its own certificate and key, from files, a mounted secret, Secrets Manager, or env vars that point at files. Find it with:

grep -rnE "pfx|passphrase|SNICallback|addContext|createSecureContext|(key|cert)[[:space:]]*:[[:space:]]*(fs\.)?readFileSync|\.(pem|key|crt|pfx|p12)['\"]" --include='*.js' --include='*.mjs' --include='*.cjs' --include='*.ts' src/

Node has no global key store: there is no equivalent of javax.net.ssl.keyStore. Certificates always reach tls.createSecureContext as PEM or PFX buffers, whether a framework reads them for you (Fastify https, NestJS httpsOptions) or your code does. I. Certificate or key pinning, HSM and KMS-backed keys

Pinning: an SPKI SHA-256 pin checked in checkServerIdentity keeps working with X25519MLKEM768, and a wrong pin is still rejected (Tested, all four runtimes, pin.cjs). The key exchange doesn't change the server's certificate or key, so existing pins stay valid. Pins on ML-DSA certificates are a separate change (see Certificates (ML-DSA)).

HSM / PKCS#11 / KMS: the server's private key only signs the handshake; the ML-KEM key exchange is ephemeral and doesn't use it. Node can load keys through OpenSSL engines (privateKeyEngine, privateKeyIdentifier, clientCertEngine); engines are deprecated in OpenSSL 3 and this path was not tested. Node has no hook for a KMS-held TLS key: terminate TLS at an ALB/NLB with ACM instead (see Load balancers). Unverified for HSM-backed keys.

J. Other cases

  • HTTPS proxy (HTTPS_PROXY, CONNECT tunnel): the TLS session runs end to end from Node through the tunnel, so the PQ outcome is Node's. A TLS-inspecting proxy re-terminates and its own stack decides (see Network devices and egress). Not tested here.
  • HTTP/2 and gRPC servers: covered in B and C (Tested).
  • WebSockets (wss:// with ws): uses node:tls, expected to follow Node. Not tested.
  • Service mesh sidecar: the app speaks plaintext to the sidecar; the mesh decides (see Service mesh).
  • NODE_TLS_REJECT_UNAUTHORIZED=0 or rejectUnauthorized: false: doesn't affect PQ, but turns off the trust checks that cases D and E rely on. Remove it while you are in the code.
