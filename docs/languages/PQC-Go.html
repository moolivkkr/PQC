1 Summary for Go teams

What decides PQ. Go's own crypto/tls is compiled into the binary, so the OS, base image and Lambda runtime play no part. Three things decide the result: the toolchain version, the go line in go.mod, and any explicit TLS settings in code. A binary built with Go 1.24+ and a go line of 1.24+ negotiates X25519MLKEM768 by default on every compute type.

Compute PQ today? What to change
Lambda (provided.al2023, provided.al2) Yes with Go 1.24+ and go ≥ 1.24 Rebuild with Go 1.26, raise the go line; or GODEBUG=tlsmlkem=1
ECS Fargate, ECS on EC2, EKS Same rule; the base image does not matter Same
EC2 Same rule Same; the systemd unit can carry GODEBUG

What to change, in order

  1. go version -m <binary> shows Go 1.23 or older: rebuild with Go 1.26. Nothing else helps (1.23 offers only the pre-standard Kyber draft).
  2. The go line is below 1.24: raise it to 1.26. If you can't yet, godebug tlsmlkem=1 in go.mod or GODEBUG=tlsmlkem=1 in the deployment.
  3. Code or a library sets CurvePreferences or MaxVersion: tls.VersionTLS12: add X25519MLKEM768 or remove the setting.
  4. FIPS mode: use Go 1.26+ native FIPS 140-3 (1.24 has no PQ in FIPS mode; fips140=only on 1.25 fails every handshake). The AWS SDK for Go v2 in FIPS mode forces classical curves: re-add the hybrids with WithTransportOptions.

Certificates and keystores: no change. Watch two things: SSL_CERT_FILE replaces the system bundle rather than adding to it, and x/crypto/pkcs12 cannot read OpenSSL 3 PKCS#12 files (use go-pkcs12). ML-DSA: Go 1.23 to 1.27 never negotiate ML-DSA in TLS; they get the ECDSA certificate from a dual-certificate server and fail an ML-DSA-only one.

Rollback: GODEBUG=tlsmlkem=0,tlssecpmlkem=0 in the environment; no rebuild. Detect: CloudTrail for AWS calls; Go 1.25+ can log ConnectionState().CurveID itself.

Tested: 118 client cases (Lambda 77, Fargate 22, ECS on EC2 5, EC2 14) and 5 load balancer target cases, all passing, covering Go 1.23 to 1.27, every go line, GODEBUG, FIPS modes and the AWS SDK fix.

2 Context for application teams

2.1 What "PQC-enabled" means

A PQ connection is a TLS 1.3 handshake that negotiated a hybrid ML-KEM key exchange group, X25519MLKEM768 (ML-KEM is FIPS 203). It protects traffic recorded today from being decrypted by a future quantum computer. Your service is PQ-enabled when it offers or accepts that group first and still connects to classical peers, so nothing breaks. It is done when the programme's dashboards show its connections as PQ, not when the change is deployed.

What does not change: your certificates, keystores, private CA trust and mutual TLS. ML-KEM works with today's RSA and ECDSA certificates. ML-DSA (PQ certificates, FIPS 204) is a separate, later track; your summary page says what your runtime can do with it.

2.2 How the fix ships

Every fix is one of: a configuration file plus a variable, a Java agent, a base image or a version. The shared pq-tls kit versions these files once, and the shared build template adds them, so your service picks the fix up on its next release and rolls back by removing one setting. Guardrails in the pipeline warn first and fail later on settings that block PQ.

Where a variable goes How

Container images ENV NAME=value in the Dockerfile
ECS task, EKS pod (override) containerDefinitions[].environment; spec.containers[].env
EC2 service Environment=NAME=value in the systemd unit

Go's own crypto/tls, compiled into the binary, controls every handshake. All rows Tested. The rules behind the table:

  1. Toolchain sets what exists: 1.24 added X25519MLKEM768, 1.26 added the two SecP hybrids to the defaults, 1.27 added opt-in pure MLKEM1024, offered only when listed in CurvePreferences (Go 1.26, Go 1.27; Tested).
  2. The go line of the main module (or go.work) sets the defaults: below 1.24 gives tlsmlkem=0, below 1.26 gives tlssecpmlkem=0. A dependency's go.mod doesn't count (Documented; Tested).
  3. Override at build time without raising the go line: godebug tlsmlkem=1 in go.mod (Go 1.23+ toolchains) or //go:debug tlsmlkem=1 above package main. Both put tlsmlkem=1 into DefaultGODEBUG (Tested 1.24 to 1.27). Add tlssecpmlkem=1 on 1.26+ only: a 1.24 or 1.25 build fails with unknown godebug "tlssecpmlkem" (Tested, e2e build log; Documented).
  4. Run-time GODEBUG beats both: tlsmlkem=1 turns PQ on with no rebuild, tlsmlkem=0 turns it off (Tested). Unknown names are ignored at run time, so one value tlsmlkem=1,tlssecpmlkem=1 is safe on 1.24+ (Documented; tested on 1.26 only).
  5. Explicit CurvePreferences vs tlsmlkem=0. On 1.24 to 1.26, tlsmlkem=0 drops X25519MLKEM768 even from an explicit list. From 1.27 an explicit list wins (Documented; Tested both).

Raising the go line changes other defaults too. Going to 1.27 removes the tls10server, tlsrsakex, tls3des, tlsunsafeekm, x509keypairleaf and asynctimerchan settings (Go 1.27; Documented), so run the service tests. The GODEBUG route changes only the TLS groups.

Every case below was tested with Go 1.24.13 (go 1.24), 1.25.14 and 1.26.11 against OpenSSL 3.5.7 and Go test servers, unless a row says otherwise; Go 1.23.12 and go 1.22/1.23 builds were classical in every row, so the case was never the cause. Programs: tests/deep/go/v2/cases/main.go, tests/deep/go/v2/deps/main.go; outputs: tests/deep/go/v2/run-v2.out, run-v2b.out, run-v2c.out.

A. Simple client

Who this is. No TLS settings in code: grep -rnE --include='*.go' 'tls\.Config|TLSClientConfig|CurvePreferences|MaxVersion' . finds nothing. You use http.Get, the AWS SDK default client, or a driver with a DSN.

What happens today. PQ when the toolchain and the go line are both 1.24+; classical otherwise (Tested). What to change. Nothing in code: raise the go line and rebuild. Side effects. The ClientHello grows by about 1.2 KB (Pitfalls).

Rule for every library: pass a tls.Config without CurvePreferences, or none. Tested with Go 1.26.11 (go 1.26) against a Go server that accepts only X25519MLKEM768:

cfg := &tls.Config{CurvePreferences: []tls.CurveID{
    tls.X25519MLKEM768, tls.SecP256r1MLKEM768, tls.X25519, tls.CurveP256}}

What to change. Nothing in the store: same files, formats, passwords, key types and chains. The tls.Config your loader fills must not set CurvePreferences without a hybrid, nor MaxVersion: tls.VersionTLS12. The one code change any team may need is the PKCS#12 import:

// Was golang.org/x/crypto/pkcs12 (frozen; can't read OpenSSL 3 default files)
import pkcs12 "software.sslmate.com/src/go-pkcs12"

key, leaf, chain, err := pkcs12.DecodeChain(p12Bytes, os.Getenv("TLS_KEY_PASS"))
c := tls.Certificate{PrivateKey: key, Leaf: leaf, Certificate: [][]byte{leaf.Raw}}
for _, ca := range chain { c.Certificate = append(c.Certificate, ca.Raw) }
cfg := &tls.Config{Certificates: []tls.Certificate{c}} // no CurvePreferences

The alternative, re-exporting with openssl pkcs12 -export -keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1, keeps 3DES and SHA-1, so prefer the import change. x/crypto/pkcs12 is frozen and its docs point to go-pkcs12 (Documented).

Encrypted keys. The standard library can't read encrypted PKCS#8, and x509.DecryptPEMBlock is deprecated as insecure by design (Documented). In order of preference: keep the key unencrypted inside a secret store (Secrets Manager, Kubernetes Secret, ECS secrets) and load it with tls.X509KeyPair; decrypt at start-up with youmark/pkcs8, the passphrase from Secrets Manager; or move the key to KMS or an HSM (case I). All three loaders were tested above.

Side effects. None for PQ. If RSA is listed before EC, default clients get RSA; that was already true.

E. Mutual TLS (client certificates)

Who this is. grep -rnE --include='*.go' 'ClientAuth|ClientCAs|GetClientCertificate|Certificates:' .

What happens today. Client certificates don't change the group (Tested; client side also in e2e: GetClientCertificate, PEM from env vars, PKCS#12):

  • Go client with an RSA cert in Certificates or an EC cert from GetClientCertificate: X25519MLKEM768 to a PQ-only mTLS server, X25519 to a classical one.
  • Go server with ClientAuth: tls.RequireAndVerifyClientCert: RSA and EC clients over X25519MLKEM768, client_cn logged; classical clients over X25519.
  • No client cert: refused. In TLS 1.3 the client sees remote error: tls: certificate required on its first read; the server logs tls: client didn't provide a certificate.

What to change. Nothing. Side effects. None.

    CurvePreferences: []tls.CurveID{tls.X25519MLKEM768, tls.SecP256r1MLKEM768}}

Side effects. Removing MaxVersion lets TLS 1.3 through; check peers that pin TLS 1.2 behaviour, such as inspection proxies.

I. Pinning, and HSM, PKCS#11 or KMS keys

Who this is. VerifyPeerCertificate or VerifyConnection with SPKI hashes; a tls.Certificate whose PrivateKey is a KMS, CloudHSM or PKCS#11 crypto.Signer.

What happens today.

  • SPKI pinning in VerifyConnection: the right pin passed over X25519MLKEM768 and X25519; a wrong pin failed with your error (Tested 1.24.13, 1.26.11; also e2e). Key exchange doesn't touch certificates, so pins stay valid until you move to ML-DSA certificates.
  • A server key behind an opaque crypto.Signer (only Public and Sign), RSA and EC: Sign was called once per handshake and X25519MLKEM768 was negotiated (Tested 1.24.13, 1.26.11). ML-KEM runs in software in crypto/tls; the HSM only signs. A real KMS, CloudHSM or PKCS#11 module was not tested (Unverified).

What to change. Nothing. Side effects. None.
